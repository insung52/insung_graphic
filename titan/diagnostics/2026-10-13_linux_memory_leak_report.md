# 리눅스 호스트 메모리 누수 원인 분석 및 조치 보고

2026-10-13 / 완료 / 리눅스 호스트의 메모리 증가(≈40 MB/분)는 UE 5.8.2 Vulkan RHI 엔진 버그 2건이 원인이었고, 설정 2줄로 우회해서 15.5시간 연속 실행 기준 ≈0.5 MB/분까지 낮춤.

---

## 1. 요약

| 항목 | 내용 |
|---|---|
| 증상 | 리눅스 호스트 PC에서 실행 시간에 비례해 메모리(RSS)가 일정한 속도로 증가. 윈도우 PC는 증가 없음 |
| 원인 | 언리얼 엔진 5.8.2의 Vulkan 렌더링 모듈 버그 2건 (프로젝트 코드 문제 아님) |
| 조치 | 엔진 설정 2줄 추가 (`Config/Linux/LinuxEngine.ini`) — 엔진 수정·재빌드 불필요 |
| 결과 | 증가 속도 **≈40 MB/분 → 0.8 MB/분** (약 98% 감소), 프레임레이트 영향 없음 |
| 장시간 확인 | 15.5시간·113회 연속 실행에서 ≈0.5 MB/분, 스왑 0, 프레임레이트 저하 없음 |

**운영 영향**: 조치 전에는 메모리 15 GB PC 기준으로 약 3~4시간이면 메모리가 거의 다 차서, 화면 멈춤(스왑 사용) 뒤에 시스템이 프로그램을 강제 종료할 수 있는 상태였다. 조치 후에는 10시간 연속 실행에도 증가량이 약 0.5 GB라 전시 운영에 문제가 없는 수준이다.

---

## 2. 증상

- 측정 도구: 프로젝트 내장 상태 기록기(블랙박스, `Saved/HealthLogs/*/health.csv`, 1초 간격 기록)
- 2026-10-12 2-PC(리눅스 호스트 + 윈도우 클라이언트) 실행, 약 2시간:
  - 리눅스 호스트 메모리 **4.4 GB → 9.2 GB**, 약 40 MB/분으로 일정하게 증가
  - 게임 오브젝트 수, 액터 수, GPU 메모리(VRAM)는 일정 → 게임 데이터가 늘어난 게 아님
  - 윈도우 클라이언트(D3D12)는 증가 없음 → 리눅스 전용 그래픽 경로(Vulkan) 의심
- RTSP 영상 송출(GStreamer)은 접속 클라이언트가 없을 때 데이터를 만들지 않는 구조라 원인에서 제외

---

## 3. 원인 1 — Vulkan 병렬 렌더 패스 정보 미해제 (약 40 MB/분 중 대부분)

**내용**
- 엔진은 한 프레임을 여러 렌더 패스로 나누고, 여러 스레드에서 동시에 준비한다(병렬 렌더 패스).
- Vulkan 모듈이 이 병렬 패스마다 내부 정보 구조체(약 0.9 KB)를 새로 만드는데, 패스를 닫을 때 바깥 구조체만 지우고 안쪽 구조체는 지우지 않는다.
- 엔진 소스 근거: `Engine/Source/Runtime/VulkanRHI/Private/VulkanContext.cpp:590`(생성), `:667`(바깥만 삭제), `VulkanContext.h:49-55`(소멸자 없음)

**외부 확인**
- Epic 공식 이슈 **UE-392081**로 등록된 알려진 버그. 2026-09-22 기준 "Ready for QA" 상태이고, 5.8.3 핫픽스에도 수정이 포함되지 않았다.
- Epic 포럼 보고: https://forums.unrealengine.com/t/ue-5-8-2-vulkan-memory-leak-consumed-114gb-ram-and-killed-by-oom/2764868

**조치**
- `r.Vulkan.RHIThread=1` — 그래픽 명령 처리 스레드를 단일 구성으로 바꾸면 엔진이 병렬 렌더 패스를 쓰지 않는다(`VulkanRHI.cpp:979-985`). 버그 코드가 실행되지 않는다.

**효과** (85분 실행)

| | 조치 전 | 조치 후 |
|---|---|---|
| 메모리 증가 | ≈40 MB/분 | ≈11.5 MB/분 |
| 평균 프레임레이트 | 57.7 fps | 58.0 fps |
| RHI 스레드 최대 처리 시간 | 7.1 ms | 12.4 ms (프레임 예산 안) |

## 4. 원인 2 — 업로드용 임시 버퍼의 디버그 기록 미해제 (남은 ≈11.5 MB/분)

**찾은 과정**
1. 엔진 메모리 분류 기록(LLM)으로 실행 → 렌더링 하위 분류(RHIMisc)만 직선으로 증가
2. 전체 메모리 할당 추적(메모리 트레이스) → 교전 중 7~16 MB/분, 대기 화면 ≈2 MB/분 → **교전량에 비례**
3. Unreal Insights로 교전 10분 구간에서 할당 후 해제되지 않은 메모리 집계 → 113 MB(= 11.3 MB/분, 실측과 일치), 1위는 **80바이트 할당 약 21만 개**
4. 해당 할당의 호출 경로를 추적:
   `렌더 그래프 버퍼 업로드(FRDGBuilder::SubmitBufferUploads)` → `버퍼 잠금(FVulkanBuffer::Lock)` → `임시 업로드 버퍼 대여(FStagingManager::AcquireBuffer)` → `80바이트 할당`

**내용**
- GPU로 데이터를 올릴 때 엔진은 임시 업로드 버퍼(스테이징 버퍼)를 빌려 쓴다.
- 개발용 빌드(Development)에서는 버퍼를 빌려줄 때마다 디버깅용으로 "누가 빌려갔는지" 호출 기록 배열(주소 10개 = 80바이트)을 만든다.
- 그런데 버퍼를 지울 때 이 기록 배열은 해제하지 않는다. 버퍼가 만들어지고 지워질 때마다 80바이트씩 남는다.
- 교전 중에는 이펙트·파티클 데이터 업로드가 많아서 버퍼 생성·삭제가 잦고, 그만큼 빨리 쌓인다.
- 엔진 소스 근거: `VulkanMemory.cpp:128`(기록 깊이 기본값 10), `:362`(배열 생성), `:4361`·`:4393`(버퍼 삭제 시 배열 해제 없음)
- 최종 배포용 빌드(Shipping)에는 이 기록 기능이 없어서 해당하지 않는다.

**추가 확인**
- 엔진 진단 명령(`r.Vulkan.DumpStagingMemory`)으로 실행 중 임시 버퍼 개수를 두 번 확인했다. 두 번 모두 약 300개로 일정했다. 버퍼 자체는 정상적으로 지워지고 기록 배열만 남는다는 판단과 맞는다.

**조치**
- `r.Vulkan.MemoryBacktrace=0` — 호출 기록 대신 소스 파일명·줄 번호만 저장하게 해서 할당이 생기지 않는다.
- 영향: 엔진 메모리 디버그 출력에서 호출 기록이 빠지는 것뿐이다. 화면·성능 영향은 없다.

**효과** (60분 실행, 전투 시나리오 7회 완주)

| | 조치 전 | 조치 후 |
|---|---|---|
| 메모리 증가 | ≈11.5 MB/분 | **≈0.8 MB/분** |
| 스왑 사용 | — | 0 |
| 평균 프레임레이트 | — | 57.8 fps |

## 5. 적용 내용

파일: `Config/Linux/LinuxEngine.ini` (리눅스 패키지에만 적용)

```ini
[SystemSettings]
r.Vulkan.RHIThread=1
r.Vulkan.MemoryBacktrace=0
```

- 두 값 모두 엔진 시작 시 한 번만 읽히므로 실행 중 콘솔로는 바꿀 수 없다. ini 또는 실행 인자(`-dpcvars=`)로 바꾼다.
- 패키징 시 자동으로 포함된다. 엔진 수정이나 재빌드는 필요 없다.
- 일시 원복 방법: 실행 인자 `-dpcvars=r.Vulkan.RHIThread=2,r.Vulkan.MemoryBacktrace=10`
- 엔진을 버그가 수정된 버전으로 올리면 두 줄을 다시 검토해서 제거한다.

## 7. 장시간 실행 확인 (2026-10-13~14)

- 설정 반영 패키지, 실행 인자 없이 ini만으로 적용 확인(로그 `Set CVar [[r.Vulkan.MemoryBacktrace:0]]`)
- 약 15.5시간, 전투 시나리오 113회 연속 실행
- 메모리(rss_anon) 3,234 → 3,705 MB, **≈0.5 MB/분** (전반 0.58, 후반 0.45 MB/분)
- 스왑 0, 게임 오브젝트 수·VRAM 일정, 프레임레이트 저하 없음(첫 회 57.2 → 마지막 57.7 fps)
- 잔여 ≈0.5 MB/분의 작은 증가는 남아 있다. 하루 10시간 운영 시 약 0.3 GB 수준이라 운영 영향은 없다고 판단하고, 블랙박스로 계속 감시한다. 원인은 미조사이며, 엔진 내부일 가능성이 높다(같은 설정의 외부 사용자도 별개의 소량 잔여 증가를 보고함).

## 8. 엔진 5.8.3 업데이트로 해결되는가

**결론: 해결되지 않는다. 두 누수 모두 5.8.3에서 고쳐졌다는 근거가 없으므로, 5.8.3으로 올려도 위 설정 2줄은 유지해야 한다.** (2026-10-13 기준, 현재 프로젝트 엔진은 5.8.2 CL 56702186)

| 누수 | 5.8.3 수정 여부 | 근거 |
|---|---|---|
| 원인 1 (병렬 렌더 패스, UE-392081) | **미포함** | 5.8.3 핫픽스 공지의 수정 목록 전체에 Vulkan·메모리 누수·RHI 관련 항목이 없음. UE-392081은 2026-09-22 "Ready for QA"(검증 대기) 상태이고, 수정 목표 버전이 공개되지 않음. 포럼 스레드 마지막 글(09-30)에서도 5.8 사용자가 같은 누수와 `r.Vulkan.RHIThread=1` 우회를 보고함 |
| 원인 2 (임시 업로드 버퍼 디버그 기록) | **미포함** | 공개된 버그 보고 자체가 없음(이번 분석에서 처음 확인). 5.8.3 수정 목록에도 해당 항목 없음. 비슷한 증상의 과거 이슈 UE-350403(안드로이드, 스테이징 버퍼 증가)은 "재현 불가"로 종료됨 |

- 출처
  - 5.8.3 핫픽스 공지: https://forums.unrealengine.com/t/5-8-3-hotfix-released/2833315
  - UE-392081 관련 포럼: https://forums.unrealengine.com/t/ue-5-8-2-vulkan-memory-leak-consumed-114gb-ram-and-killed-by-oom/2764868
  - UE-350403: https://issues.unrealengine.com/issue/UE-350403
- 2026-10-13 기준으로 5.8.4 핫픽스는 공개되지 않았다.
- 주의: 핫픽스 공지는 주요 수정만 나열하므로, 최종 확인은 5.8.3 엔진 소스를 직접 보는 게 확실하다. 5.8.3을 설치하면 아래 두 곳만 확인하면 된다.
  - 원인 1: `Engine/Source/Runtime/VulkanRHI/Private/VulkanContext.h`의 `FVulkanParallelRenderPassInfo`에 소멸자(`~FVulkanParallelRenderPassInfo`)가 생겼는지, 또는 `VulkanContext.cpp`의 `RHIEndParallelRenderPass`가 `DynamicRenderingInfo`를 지우는지
  - 원인 2: `Engine/Source/Runtime/VulkanRHI/Private/VulkanMemory.cpp`의 `FStagingBuffer::~FStagingBuffer()` 또는 `Destroy()`에 `VULKAN_FREE_TRACK_INFO(Track)`가 생겼는지
- 엔진 업데이트 후에도 설정은 그대로 두는 게 안전하다. 두 설정 모두 성능·화면 영향이 없어서, 버그가 고쳐진 엔진에서 남아 있어도 손해가 없다. 제거는 소스 확인과 장시간 실행 측정을 마친 뒤에 한다.
- 원인 2는 Epic에 버그 보고를 해 두면 이후 버전에서 수정될 가능성이 있다(선택).

## 참고 — 메모리가 바닥날 때 리눅스의 동작

- 먼저 스왑(디스크 가상 메모리, 기본 약 2 GB)을 쓰기 시작하면서 화면이 수 초~수 분씩 멈춘다. 이때 로그는 에러 없이 비어 있다.
- 스왑까지 차면 운영체제(systemd-oomd 또는 커널 OOM killer)가 메모리를 가장 많이 쓰는 프로세스(= 시뮬레이터)를 강제 종료한다. 에러 창이나 크래시 보고 없이 창이 사라진다.
- 사후 확인 방법: `journalctl -k | grep -i -E "out of memory|oom"` 또는 블랙박스 `health.csv`의 `rss_anon_mb`·`swap_used_mb` 열.
