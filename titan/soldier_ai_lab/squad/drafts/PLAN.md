## 0. 이 문서의 범위와 경계

### 0.1 담당 범위 (이 문서가 정하는 것)

| 영역 | 내용 |
|---|---|
| 분대 표현 | 편제 데이터 구조, 역할, 조(Element), 분대장 승계 |
| 명령 분해 | L0 `FSoldierOrder` → L1 플랜 선택 → L2 `FSquadAssignment` |
| 협동 전술 | 바운딩 오버워치 · 측면기동 · 집중사격 · 후퇴 · 재편성의 **배분 규칙** |
| 정보 공유 | 접촉 보고의 지연·불확실성·병합 규칙 |
| 자원 중재 | 엄폐 슬롯 / 표적 / 토큰의 **중재 규칙** |
| 성능 | 분대 틱 스케줄링, 개인 계산과의 분담 경계 |

### 0.2 명시적 비담당 (다른 담당자 / 다른 층)

| 영역 | 소유 | 이 문서의 취급 |
|---|---|---|
| 개인 지각·시야·청각·위협 평가 | 인지 담당 (설계 7절) | **소비만 한다.** `ISoldierThreatMemorySink` 인터페이스로 접촉 보고를 밀어넣을 뿐, 기억 구조를 정의하지 않는다 |
| 엄폐 지점 **생성·평가** | 엄폐 담당 (설계 10.1~10.2·10.4절) | **중재 규칙만.** EQS 질의 설계·슬롯 베이크·가중치는 건드리지 않는다 |
| 개인 유틸리티 스코어러(L2) | 설계 8절 | **입력을 공급만 한다.** 축 커브·점수 공식을 정하지 않는다 |
| Intent별 StateTree 서브트리 내용(L3) | 설계 4.1절(상위계획) | 토큰 태스크와 분대 Evaluator의 **삽입 지점**만 규정 |
| 분대 **간** 조율 | L0 COMMAND | **하지 않는다.** 여러 분대의 협동은 L0가 각 분대에 별도 명령을 내려 표현한다 (0.3 참고) |

### 0.3 새로 못박는 경계 규칙 【신규】 [A]

> **L1은 분대 하나 안에서만 조율한다. 분대 간 조율은 L1에 없다.**

근거: 설계 2.1절 제1규칙("이 결정을 내리려면 무엇을 알아야 하는가") — "2분대가 좌측을 맡는 동안
1분대가 제압한다"를 알려면 **전장 전체**를 알아야 하고, 그건 L0의 정보 범위다. L1에
분대 간 협상을 넣으면 L0가 비어버리고 L1이 L0가 된다(설계가 피하려는 계층 붕괴).

**단 하나의 예외**: 자원 중재 중 **엄폐 슬롯**은 분대 경계를 넘는 경쟁이 실제로 일어난다.
이것은 L1이 아니라 **SmartObject 예약(엔진 기능, 설계 10.3절)** 이 처리한다 — 5.1절 참고.

## 2. 분대 표현

### 2.1 어디에 사는가 — `ASquadCoordinator` + `USquadComponent` 【신규】 [A]

설계 3.7절은 `Squad/ USquadComponent, FSquadBlackboard`라고만 적었고 **어느 액터에 붙는지**를
정하지 않았다. 후보는 셋이다.

| 안 | 문제 |
|---|---|
| (a) 분대장 폰에 붙인다 | **분대장이 죽으면 분대 상태가 함께 파괴된다.** 설계 9.5는 "사망 시 차순위 승계"를 요구하는데, 그러려면 blackboard·토큰·플랜을 새 액터로 이전해야 한다. 이전 중 한 틱이라도 비면 전원이 토큰을 잃는다 |
| (b) `USquadSubsystem`이 구조체로만 보관 | UObject가 아니라 에디터 디테일 패널·`Rewind Debugger`·BP 노출이 전부 사라진다. 설계 10절(관찰 가능성, 상위계획)이 요구하는 "L1: 현재 플랜, 슬롯 배정도, 토큰 현황, 사기 게이지"를 볼 방법이 없다 |
| **(c) 전용 호스트 액터** ← **채택** | 액터 1개/분대 × 최대 11개. 비용은 무시할 수준이고 위 둘의 문제가 모두 없다 |

```
ASquadCoordinator : AInfo          ← 서버 전용 스폰, 렌더링 없음, 분대원 수명과 무관
   └ USquadComponent              ← 설계 3.7절의 이름 그대로. 모든 L1 로직
        └ FSquadBlackboard        ← 설계 9.3절 구조체
USquadSubsystem : UTickableWorldSubsystem
   ├ 분대 등록/조회 (SquadId → Coordinator)
   ├ 액터 → 분대 역인덱스 (개인이 자기 분대를 찾는 경로)
   └ 라운드로빈 스케줄러 (7.2절)
```

**멤버 인덱스는 재사용하지 않는다** [A] — 전사자를 배열에서 제거하지 않고 `HealthState=Dead`로
표시만 한다. 이유: `FSquadHandle{SquadId, MemberIndex}`를 개인이 캐시하는데, 제거하면 인덱스가
밀려 다른 사람을 가리킨다. 분대 최대 12명이라 죽은 슬롯을 들고 있는 비용은 무의미하다.

### 2.2 역할은 **둘**이다 — 편제 역할 / 전술 배역 【신규】 [A]

설계 문서 안에서 "역할"이 두 가지 다른 뜻으로 쓰이고 있다:

- 9.1절 "분대는 **슬롯/역할**을 배분" — 정적인 느낌
- 9.2절 플랜 표의 "역할 배분: 팀 A 엄호 ↔ 팀 B 전진, 도착하면 교대" — 명백히 **매 틱 바뀌는 것**

같은 낱말로 두면 "분대장이 저격수가 됐다" 같은 버그가 조용히 생긴다. **분리한다.**

| 개념 | 이름 | 성질 | 바뀌는 때 | 저장 위치 |
|---|---|---|---|---|
| **편제 역할** | `ESquadRole` | 정적 데이터 | 스폰 시 / 분대장 승계 시만 | `FSquadMemberEntry::Role` |
| **전술 배역** | `ESquadTask` | 동적 배분 | 플랜 전환·토큰 회수 시 | `FSquadAssignment::Task` |

```
ESquadRole   : Leader, Rifleman, AutomaticRifleman, Grenadier, Marksman, Medic
ESquadTask   : None, Overwatch, Bound(전진), Suppress(고정·제압),
               Maneuver(측면기동), RearGuard(후위엄호), Withdraw(이탈), Regroup
```

**편제 역할이 하는 일은 세 가지뿐이다** [B] — 그 이상 늘리지 않는다:

| # | 용도 | 어디에 |
|---|---|---|
| 1 | 배역 배분 시 **가중치** | 지원화기수는 `Suppress` 선호, 저격수는 `Overwatch` 선호. 6.3절 토큰 우선순위 |
| 2 | 토큰 **초기 배당** | `AutomaticRifleman`은 제압 토큰 요청 시 +가중 |
| 3 | 개인 프로파일 선택 | `Profile_Leader` 등 (상위계획 5.3절) — L2가 읽는다 |

> **하지 말아야 할 것** [A]: 역할별로 코드 분기를 두는 것. 설계 3.7.1절(아군/적군 코드 한 벌,
> `CLAUDE.md` P4)의 같은 논리가 역할에도 적용된다. **역할은 데이터고, 가중치로만 작동한다.**

### 2.3 조(Element) — 바운딩 오버워치의 실체 【신규】 [A]

설계 11.2절 `EOrderRecipientType`에 이미 `Element`가 있는데 L1에 대응 개체가 없었다.
바운딩 오버워치·측면기동·교대 후퇴는 **전부 "두 덩어리"** 를 요구하므로 조가 없으면 표현할 수 없다.

```
FSquadElement { FName ElementId; uint32 MemberMask; ESquadTask Task; FVector Anchor; }
```

- 분대는 **항상 2개 조**로 나뉜다 [B] (Alpha / Bravo). 3개 이상은 5~6명 분대에서 의미가 없고
  플랜 전환 로직만 복잡해진다. 12명 분대가 필요해지면 그때 재검토 → **[Q24]**
- 조 편성은 **플랜 전환 시에만** 다시 한다. 매 틱 재편성하면 분대원이 두 조를 왕복한다
- 편성 규칙 [B]: 분대장과 부분대장(승계 1순위)을 **서로 다른 조**에. 그 다음 지원화기수를 갈라
  각 조가 화력을 갖게 하고, 나머지는 위치 기준(적 방향 축에 대한 좌/우)으로 나눈다

### 2.4 `FSquadBlackboard` — 설계 9.3절 + 추가 6필드

설계 9.3절 원본을 **한 필드도 지우지 않고** 아래를 더한다. 각 필드가 왜 필요한지 명시한다.

| 추가 필드 | 왜 | 절 |
|---|---|---|
| `TArray<FSquadElement> Elements` | 조 편성 | 2.3 |
| `TArray<FPendingContactDelivery> ReportQueue` | 접촉 보고 지연 배달 | 5.2 |
| `TArray<FSlotSoftClaim> SlotClaims` | 엄폐 슬롯 사전 예고 | 6.1 |
| `TMap<TWeakObjectPtr<AActor>, uint8> TargetEngagedCount` | 표적 과집중 억제 | 6.2 |
| `TArray<FSquadFireLane> ActiveFireLanes` | 제압 사격선 회피 | 6.4 |
| `FVector RallyPoint` / `float Dispersion` | 재편성 | 4.5 |

**보관 상한** [B] — 45명 예산의 실질 방어선이다:

| 배열 | 상한 | 초과 시 |
|---|---|---|
| `KnownThreats` | **8** | `ThreatLevel × Confidence` 최하위 축출 |
| `SlotClaims` | 멤버 수 | 멤버당 1개(최신이 이전 것을 덮어씀) |
| `ReportQueue` | **32** | 가장 오래된 것부터 폐기(= 무전이 밀렸다) |
| `ActiveFireLanes` | `SuppressionTokens` | 토큰 없이는 lane도 없다 |

## 3. 명령 계층 — L0가 내리는 것과 L1이 분해하는 것

### 3.1 계약은 이미 정해져 있다 【설계】 [A]

```
L0 → L1   FSoldierOrder       (설계 11.2절 — 한 글자도 안 바꾼다)
L1 → L2   FSquadAssignment    (상위계획 8절 — 필드를 이 문서가 채운다)
L1 → L0   FOrderStatusReport  (설계 11.5절 — 그대로)
```

### 3.2 `FSquadAssignment` 필드 확정 【신규】(계약 자체는 【설계】상위계획 8절) [B]

상위계획 8절은 이름만 있고 필드가 없었다. **"제약을 주지 명령을 주지 않는다"(설계 2.2절 제2규칙)**
를 필드 하나하나에 적용해 채운다.

| 필드 | 뜻 | 제약인가 명령인가 |
|---|---|---|
| `Task` | 전술 배역 (`Overwatch`/`Bound`/…) | **제약** — "너는 지금 엄호 쪽이다". 무엇을 쏠지·어디 설지는 안 정함 |
| `Corridor` (`FBox`) | 이동 허용 영역 | **제약** — 이 밖으로 나가지 마라. 안에서는 자유 |
| `Anchor` (`FVector`) | 배역의 공간 기준점 | **제약** — bound 목표선 / 경계 구역 중심 / 집결점. **"이 좌표로 가라"가 아니다** |
| `SectorYawRange` | 담당 부채꼴 | **제약** — 설계 9.2 `Hold`의 "부채꼴 시야 분담" |
| `bHasSuppressionToken` / `bHasMovementToken` | 자원 보유 | **제약** — 없으면 해당 Intent 점수가 0 (설계 9.5) |
| `FocusTarget` | 분대 집중 표적 | **권고** — 개인 표적 선택 축의 +보너스일 뿐, 강제 아님 (6.2절) |
| `PlanAggression` | 명령 공세성 × 플랜 보정 | **제약** — EQS 가중치(설계 10.4)와 개인 축 입력 |
| `Revision` | 변경 감지용 카운터 | — |

> **위반 감시 규칙** 【신규】 [A]: `FSquadAssignment`에 **"어느 적을 쏴라" · "언제 쏴라" ·
> "정확히 이 좌표에 서라"** 에 해당하는 필드를 추가하려는 순간이 오면, 그건 설계 2.2절
> 제2규칙 위반이고 `titan_example`의 원격조종 상태로 돌아가는 첫 걸음이다.
> **필드 추가 시 이 표에 "제약인가 명령인가"를 채우게 강제한다.**

### 3.3 Verb × 상황 → 플랜 선택표 【설계 11.3의 4줄을 전체로 확장】 [B]

설계 11.3절이 4줄만 예시했다. 나머지를 채우되 **새 플랜은 1개만 추가**한다(`FormationMove`).

| Verb | 접촉 | 사기 | 추가 조건 | → 플랜 | 근거 |
|---|---|---|---|---|---|
| `Advance` | O | 높음 | — | **`BoundingOverwatch`** | 【설계】11.3 |
| `Advance` | O | 낮음 | — | `BaseOfFire` | 【신규】 사기 낮은데 전진 강행은 전멸 |
| `Advance` | X | — | — | **`FormationMove`** | 【설계】11.3 "대형 이동"에 이름을 붙인 것 |
| `Engage` | — | 높음 | 측면 경로 O **AND** `bAllowFlanking` | **`Flank`** | 【설계】11.3 |
| `Engage` | — | 보통↑ | 그 외 | **`BaseOfFire`** | 【설계】11.3 |
| `Engage` | — | 낮음 | — | `BaseOfFire` (제압 토큰 −1) | 【신규】 |
| `Suppress` | — | — | — | `BaseOfFire` (제압 토큰 **상한↑**) | 【신규】 Suppress는 별도 플랜이 아니라 BaseOfFire의 토큰 설정 차이다 |
| `Occupy` / `Overwatch` | — | — | — | **`Hold`** | 【설계】9.2 |
| `Withdraw` | — | — | — | **`Withdraw`** | 【설계】9.2 |
| `Regroup` | — | — | — | **`Regroup`** | 【설계】9.2 |
| `MoveTo` / `Follow` | — | — | — | `FormationMove` | 【신규】 `Follow`는 Anchor가 고정점이 아니라 액터 |
| `HoldFire` | — | — | — | **플랜 유지. ROE만 바꾼다** | 【신규】 ★ |

**두 개의 무조건 오버라이드(플랜 선택보다 먼저 판정)** 【신규】 [B]:

```
if (Morale < MoraleCollapseThreshold && Morale > Constraints.MoraleFloor) → Withdraw 강제
if (Dispersion > DispersionThreshold && 현재 플랜이 Regroup이 아님)      → Regroup 강제
```

`MoraleFloor`(설계 11.2)가 여기서 작동한다 — **하한이 높으면 사기가 떨어져도 Withdraw로
넘어가지 않는다** = 설계 9.4절의 "결사 항전". 하드코딩된 `LastStandZoneIndex`를 대체하는 지점.

> ★ **`HoldFire`가 플랜을 안 바꾸는 이유** [A]: `EOrderVerb`는 두 종류가 섞여 있다 —
> **위치·태세를 바꾸는 동사**(MoveTo/Occupy/Advance/…)와 **교전규칙만 바꾸는 동사**(HoldFire).
> 설계 11.2절 주석도 `HoldFire`를 "교전규칙만 바꿈"이라 적었다. 이걸 플랜으로 취급하면
> "사격 금지" 명령 하나에 분대가 진형을 풀어버린다.
> **구현 규칙**: `HoldFire`는 `Constraints.ROE`만 갱신하고 `CurrentPlan`을 건드리지 않는다.

### 3.4 플랜 선택 = 스코어 선택, 계획기 없음 【설계 9.2】 [A]

```
FinalScore(P) = RuleWeight(P)                       // DataAsset (P6: 상수를 코드에 박지 않는다)
              × Gate(P)                             // 0 또는 1 — 위 표의 조건
              × (P == CurrentPlan ? PlanHysteresis : 1.0)   // 1.15 [B]
```

- **히스테리시스 1.15** [B] — 설계 8.3절이 개인 유틸리티에 준 `+10~15%`와 같은 값·같은 이유.
  분대 결정이 개인보다 느려야 하므로(설계 4.2: "이보다 빠르면 분대 결정이 요동친다")
  최소 유지시간을 **추가로** 건다.
- **최소 플랜 유지시간 3.0초** [B]. 예외: 명령 변경 / 위 두 오버라이드 / 분대장 사망.
- 판정 기준 [C]: 5v5 교전 60초에서 **플랜 전환 횟수가 8회 이하**. 그 이상이면 요동이다 → **[C-61]**

### 3.5 역방향 — `FOrderStatusReport` 채우기 【설계 11.5】 [A]

| 필드 | L1이 어떻게 채우나 |
|---|---|
| `Status` | `Received`(배달) → `InProgress`(플랜 선택) → 아래 `Achieved` 조건 → `Failed`(전멸/도달불가) |
| `Progress` | Verb별로 다르다: `Occupy`=구역 내 생존자 비율, `Advance`=시작점→목표 축 투영 진척, `Withdraw`=이탈 완료 비율, `Engage`=`1 - 확인된 적 수/최초 확인 수` |
| `Casualties` | `HealthState == Dead\|Downed` 수 |
| `SquadMorale` / `SquadCentroid` | blackboard 그대로 |
| `ConfirmedEnemyCount` | `KnownThreats` 중 `Confidence > 0.7` 개수 [B] |

`Achieved` 판정은 **Verb별 술어 하나**로 데이터화한다 [B] — enum 분기를 늘리지 않는다.
보고 발행 주기: **상태가 바뀔 때 + 2초 주기** [B]. 매 분대 틱마다 보내면 L0가 스팸을 받는다.

## 4. 협동 전술 — 배분 규칙

**공통 원칙** [A]: L1은 **누가 어느 배역인지와 어디까지 나갈 수 있는지**만 정한다.
"언제 쏘고 언제 뛰는가"는 전부 개인(L2/L3)이다.

### 4.1 바운딩 오버워치 — ★ 설계의 "토큰만으로 창발한다"는 절반만 맞다 【신규】 [B]

설계 9.5절 / 상위계획 6.2절:
> "이동 토큰만으로 바운딩 오버워치가 창발한다 — 상한 이하로만 움직이니 나머지는 자동으로 엄호
> 상태가 된다. 별도 로직이 필요 없다."

**개인 단위로 토큰을 발급하면 이것이 성립하지 않는다.** 반례:

> 5명 분대, 이동 토큰 2개. 매 판단 틱마다 **다른 2명**이 토큰을 잡는다 →
> 전원이 조금씩 앞으로 기어가는 **산개 전진**이 나온다. 엄호선은 유지되지만
> **"한 조가 자리를 잡고 다른 조가 붙는" 교대**는 절대 나오지 않는다.
> 관찰자에게는 바운딩 오버워치가 아니라 "다들 눈치보며 야금야금 간다"로 보인다.

**수정** — 토큰의 발급 단위를 플랜이 정한다:

| 플랜 | 이동 토큰 발급 단위 | 결과 |
|---|---|---|
| `BoundingOverwatch` | **조(Element) 단위** — 한 번에 한 조가 통째로 보유 | 조 교대 = 진짜 바운딩 |
| `BaseOfFire` / `Hold` | **개인 단위** (설계 원안) | 산개 재배치. 이쪽은 원안이 맞다 |
| `Flank` | 기동조 = 조 단위 상시 보유, 고정조 = 0 | |
| `Withdraw` | 조 단위 교대 | 교대 후퇴 |

**bound 종료 조건(토큰 회수)** [B] — 하나라도 걸리면 회수하고 반대 조에 넘긴다:

| # | 조건 | 기본값 |
|---|---|---|
| 1 | 이동조 생존자의 **70%** 이상이 다음 bound line 도달 | 0.7 |
| 2 | bound 최대 지속시간 초과 (막힘/경로 실패 대비) | 8.0초 |
| 3 | 이동조에서 사상자 발생 | 즉시 |
| 4 | 엄호조가 제압 능력 상실(전원 재장전/사상) | 즉시 |

- **bound line** = `Anchor`. 계산 [B]: 분대 centroid → 목표(Order Target) 축 위에서
  `min(BoundLengthCm, 남은거리)` 앞. `BoundLengthCm` 기본 **1500cm** [C] — 너무 길면 엄호 사거리를
  벗어나고 짧으면 찔끔거린다 → **[C-62]**
- **bound 최소 지속시간 2.0초** [B]. 없으면 조건 1이 즉시 참이 되는 상황에서 토큰이 매 틱 튄다
- **교대 시 겹침** 【신규】 [B]: 이동조가 토큰을 받는 순간 엄호조 토큰을 뺏지 않고
  **0.5초 겹쳐서** 회수한다. 겹치지 않으면 "아무도 안 쏘는" 한 틱이 생긴다

### 4.2 측면기동 (Flank) 【설계 9.2】 + 회랑 생성 【신규】 [B]

설계 9.2는 "고정조(제압) + 기동조(회랑)"만 정했고, **회랑을 어디서 얻는지**가 비어 있었다.

| 소스 | 우선순위 | 방법 |
|---|---|---|
| `Constraints.CorridorId` (레벨 저작 볼륨) | **1순위** | 있으면 무조건 이것. 저작자 의도가 런타임 추정을 이긴다 |
| 런타임 생성 | 2순위 | 아래 |

**런타임 회랑 생성** [B] — 분대 틱에서 도는 유일한 공간 계산이며 **플랜 전환 시 1회만** 돈다:

```
Axis      = normalize(EnemyCentroid - FriendlyCentroid)
Side      = ±1  (아군 centroid에서 적 centroid를 봤을 때 더 짧은 경로 쪽)
CorridorC = FriendlyCentroid + Perp(Axis)*Side*FlankOffsetCm + Axis*(거리*0.5)
Corridor  = FBox(중심=CorridorC, 반경=FlankHalfExtent)
```

**검증 [A]** — 이걸 빼면 벽 안으로 회랑을 그린다:
1. `UNavigationSystemV1::ProjectPointToNavigation`로 회랑 중심의 NavMesh 투영 (동기, 1회)
2. `FindPathAsync`로 기동조 대표 1명 → 회랑 중심 경로 존재 확인 (**비동기**)
3. 실패하면 반대쪽 `Side`로 1회 재시도, 그것도 실패하면 **`Flank` 게이트를 닫고 `BaseOfFire`로 폴백**

> **`bAllowFlanking == false`면 위 계산 자체를 하지 않는다** [A] — 설계 11.2절 필드가 여기서 쓰인다.

**고정조 제약** [B]: 기동조가 회랑에 있는 동안 고정조의 이동 토큰은 **0**. 안 그러면 고정이 아니다.

### 4.3 집중사격 (Focus Fire) 【신규】 [B]

설계에 없다. 설계 9.5절은 반대 문제("동시에 다 쏘고 다 재장전")만 다뤘다.
**기본은 분산, 지시가 있을 때만 집중** — 이 방향이 설계 2.2절 제2규칙과 맞다.

| 상황 | 분대가 하는 일 |
|---|---|
| 평시 | `FocusTarget = null`. 6.2절 과집중 **억제**만 작동 |
| 고가치 표적 확인 | `FocusTarget` 지정 → 개인 `AimedFire` 표적 선택 축에 **+보너스** |
| `Order.Verb == Suppress` + `Target.Type == Actor` | `FocusTarget = 그 액터` |

**고가치 판정** [B] (분대 틱, `KnownThreats` 8개 대상 — O(8)):
`Score = ThreatLevel × Confidence × (아군을 조준 중이면 ×1.5) × (Downed면 ×0.3)`
1위가 2위의 **1.4배**를 넘을 때만 지정. 안 그러면 표적이 계속 바뀐다.

> **강제하지 않는다** [A]: 개인이 자기 눈앞의 더 급한 적을 쏘는 것을 막으면 안 된다.
> 보너스는 표적 선택 **축의 가중치**로 들어가지, 표적을 덮어쓰지 않는다.

### 4.4 후퇴 (Withdraw) 【설계 9.2 "후위 엄호조 + 이탈조, 교대 후퇴"】 [B]

바운딩 오버워치의 **부호 반전**이다 — 같은 코드를 쓴다.

| | BoundingOverwatch | Withdraw |
|---|---|---|
| Anchor 방향 | 적 쪽 | 적 반대(집결점 쪽) |
| 토큰 보유 조 | 전진조 | **이탈조** |
| 무토큰 조 배역 | `Overwatch` | `RearGuard` |
| 최초 이동조 | 목표에 가까운 조 | **적에서 먼 조** (부상자 우선 [B]) |

**후퇴 목적지** [B]: `Order.Target` → 없으면 마지막 `Hold`/`Occupy` 명령의 목표 →
그것도 없으면 **분대 스폰 위치**. 셋 다 NavMesh 투영 후 사용.

### 4.5 재편성 (Regroup) 【설계 9.2 "집결점 수렴"】 [B]

**분산도(Dispersion)** [B] = 생존자의 centroid로부터의 RMS 거리. O(N), 분대 틱마다.
`Dispersion > 2500cm`이면 `Regroup` 오버라이드 (3.3절).

**집결점** [B] — 비싼 질의를 쓰지 않는다:
`Order.Target` > 분대장 위치 > 생존자 centroid, 순서로 첫 유효값을 NavMesh 투영.

> **하지 않을 것** [A]: "가장 좋은 집결점을 EQS로 찾는다". 분대 틱에서 EQS를 발행하면
> 7.3절의 금지 규칙을 깨고 설계 12.2절의 EQS 0.7ms 예산을 분대 수만큼 잠식한다.

**해제 조건** [B]: `Dispersion < 1500cm` (히스테리시스) **AND** 최소 2초 경과.

### 4.6 Hold / FormationMove

- **`Hold`** 【설계 9.2 "전원 경계 슬롯, 부채꼴 시야 분담"】 [B]:
  `Anchor` 주변 360°를 생존자 수로 등분해 `SectorYawRange` 배분. 위협 방향이 알려져 있으면
  그쪽에 **2배 밀도**로 배분(균등 분할이 아니라 가중 분할).
- **`FormationMove`** 【신규】 [B]: 설계 11.2 `EFormationType`(Column/Wedge/Line/Diamond)을
  소비하는 유일한 플랜. 대형 오프셋 테이블(DataAsset)에서 슬롯을 뽑아 `Anchor`로 준다.
  **대형은 위치 강제가 아니라 Anchor 제공이다** — 개인은 그 주변에서 자기 경로를 만든다.

## 5. 정보 공유 — 치팅처럼 보이지 않게

### 5.1 무엇이 문제인가

설계 9.3·7.4절이 정한 것은 **`Confidence=0.6`과 `bSharedBySquad` 플래그, 둘뿐**이다. 부족하다:

| 남은 구멍 | 증상 |
|---|---|
| **즉시성** | 한 명이 본 순간 5명이 동시에 반응한다. 플레이어에게 "AI가 텔레파시를 쓴다"로 읽힌다 |
| **정밀성** | 공유 위치가 **정확한 좌표**다. 못 본 병사가 벽 뒤 정확한 지점을 조준한다 |
| **감쇠 동일성** | 들은 정보가 본 정보와 같은 속도로 낡는다 |
| **덮어쓰기** | 남의 낡은 보고가 내 방금 목격을 덮을 수 있다 |

### 5.2 3단계 모델 【신규】 [B]

```
[1] 발신 게이트 (보고할 가치가 있는가)   →  개인이 판정, L1은 접수만
[2] 지연 큐   (무전에 시간이 걸린다)     →  L1이 보관·배달
[3] 병합 규칙 (받은 것을 어떻게 믿는가)  →  수신자 개인 기억이 판정
```

**[1] 발신 게이트** [B] — 개인의 `Awareness`가 `Confirmed` 도달 시(설계 9.3 그대로) 발신하되:

| 규칙 | 값 | 왜 |
|---|---|---|
| 동일 표적 재보고 쿨다운 | **4.0초** | 없으면 한 표적이 무전을 독점한다 |
| 위치가 `LastReported`에서 이만큼 움직였으면 쿨다운 무시 | **500cm** | 적이 크게 움직이면 갱신 보고가 나가야 한다 |
| 분대 전체 무전 상한 | **2건/초** | 큐 폭주 방지. 초과분은 폐기(= 무전이 겹쳤다) |
| 사망/기절자 | 발신 불가 | 당연하지만 명시적으로 |

**[2] 지연 배달** [B]:

```
Delay(수신자) = BaseRadioDelay                      // 0.8s
              + Jitter                              // U(-0.3, +0.3)s
              + (발신자가 분대장이면 -0.3s)          // 지휘 우선
              + (수신자가 교전 중이면 +0.4s)          // "지금 바빠서 못 들었다"
Delay ∈ [0.2s, 3.0s] 클램프
```

수신자별로 지연이 **다르다**는 것이 핵심이다 — 동시에 5명이 고개를 돌리면 그 자체가 치팅 신호다.

**[3] 위치 불확실성** [B] — ★ 이 모델의 가장 중요한 항목:

```
σ = BaseSigmaCm                                     // 200cm
  + PerSecondSigmaCm × (배달시각 - 목격시각)         // 100cm/s
  + DistanceSigmaCoef × 발신자-표적 거리             // 0.05 → 20m 거리면 +100cm
σ ← min(σ, MaxSigmaCm)                              // 1500cm
```

수신자는 **좌표가 아니라 `(추정 위치, σ)`** 를 받는다. 소비 방식:

| 소비처 | σ를 어떻게 쓰나 |
|---|---|
| 조준 | **σ가 `AimSigmaThreshold`(400cm [B]) 초과면 조준하지 않는다.** 대략 방향만 본다 |
| `PeekCheck` Intent | σ가 클수록 점수↑ (설계 8.3의 "신뢰도 중간대" 축과 같은 계보) |
| 제압사격 | σ 반경을 **제압 구역**으로 쓴다 — 정확한 좌표가 필요 없는 유일한 소비처 |
| 이동 | σ 반경을 회피 비용으로 |

> **이 한 줄이 치팅 인상의 대부분을 없앤다** [B]: 남이 알려준 적은 **정조준 대상이 될 수 없다.**
> 확인하러 가거나 대략 제압할 뿐이다. 설계 7.4절이 원한 "무전으로 들었지만 나는 아직 못 봤다"의
> 실제 구현이 이것이다.

**감쇠** [B]: 공유 정보의 `Confidence` 감쇠율 = 직접 목격의 **2배**.

### 5.3 병합 규칙 — 인지 담당자와의 계약 【신규】 [A]

L1은 **병합하지 않는다.** 배달만 하고, 병합은 수신자의 개인 기억이 판정한다
(설계 2.1절 제1규칙: 내 기억을 어떻게 갱신할지는 **나만** 아는 정보다).

L1이 요구하는 계약은 인터페이스 하나다:

```cpp
ISoldierThreatMemorySink::ReceiveSharedThreat(const FSharedThreat& Report)
```

수신 측이 지켜야 하는 규칙 **3개** — 인지 담당자와 합의 필요 → **[Q23]**:

| # | 규칙 | 왜 |
|---|---|---|
| R1 | **직접 목격(`bSharedBySquad==false`)이 더 최신이면 공유 보고를 버린다.** 절대 덮어쓰지 않는다 | 내 눈이 남의 무전보다 낫다 |
| R2 | 이미 공유로 알던 것보다 오래된 보고는 버린다 | 순서 뒤집힘 방지 |
| R3 | 병합 결과의 `Confidence`는 `min(Report.Confidence, 0.6)` (설계 9.3 상한) | 들은 것이 본 것을 못 넘는다 |

### 5.4 왜 이벤트가 아니라 큐 + 폴링인가 [B]

| 안 | 문제 |
|---|---|
| 개인 → 개인 직접 브로드캐스트 | 45명 × 45명. 분대 안이라 실제로는 5×5지만 **분대 경계를 넘는 유혹**이 생긴다 |
| 델리게이트 멀티캐스트 | 지연을 표현할 자리가 없다. 지연이 이 모델의 핵심이다 |
| **큐 + 분대 틱 pop** ← 채택 | 지연이 자연스럽게 표현되고, 배달 비용이 분대 틱 예산 안에 들어온다. 큐 상한(32)으로 최악을 봉인 |

배달은 3Hz 분대 틱에서 pop하므로 **최대 0.33초의 양자화 오차**가 생긴다 [A].
지연 자체가 0.8±0.3초라 **오차가 지연 안에 묻힌다** — 문제가 아니라 오히려 지터가 공짜로 생긴다.

## 6. 자원 중재

> **범위 재확인**: 엄폐 지점의 **생성·평가**는 엄폐 담당(설계 10.1~10.2·10.4절). 여기는 **중재 규칙만**.

### 6.1 엄폐 슬롯 — SmartObject 예약 + soft-claim 【설계 10.3 + 신규 보강】 [B]

**설계가 이미 해결한 것** 【설계 9.5·10.3】 [A]: 두 명이 같은 슬롯을 **동시에 점유**하는 일은
SmartObject 예약이 막는다. 이건 그대로 쓴다.

**남아 있는 것** 【신규】: 예약은 **경쟁의 결과**만 주고 **경쟁 자체**를 막지 못한다.

> A와 B가 같은 슬롯을 최고점으로 뽑는다 → 둘 다 그쪽으로 뛴다 → 먼저 도착한 A가 예약 성공 →
> B는 도착해서야 실패를 알고 EQS를 다시 돌린다.
> **개활지를 가로질러 뛴 시간이 통째로 낭비되고, 그 구간이 가장 노출된 구간이다.**

**해법 — soft-claim(사전 예고)** [B]. 3줄이면 된다:

| 단계 | 누가 | 무엇 |
|---|---|---|
| 1 | 개인(L3) | EQS 결과 1위 슬롯을 `SquadComponent::RegisterSlotClaim(MemberIndex, SlotHandle, Score)` |
| 2 | 개인(L3) | 다음 사람의 EQS 결과에서, **이미 soft-claim된 슬롯은 점수 × `ContestedPenalty`** |
| 3 | 개인(L3) | SmartObject `ClaimSlot` 성공/실패/타임아웃 시 `ReleaseSlotClaim` |

- **`ContestedPenalty = 0.35`** [B] — **0으로 죽이지 않는다.** 설계 10.5절("완벽한 엄폐만 찾지
  않는다")과 정합하고, 남은 슬롯이 그것뿐일 때 아무도 못 가는 사태를 막는다
- **soft-claim 수명 3.0초** [B]. 이 안에 hard claim을 못 하면 자동 만료. 죽거나 멈춰버린
  분대원이 슬롯을 영구 봉인하는 것을 막는다
- **동점 처리 규칙** [B] — 점수 차가 5% 이내면 아래 순서로. **결정론이어야 한다**(리플레이·디버깅):
  1. `HealthState`가 나쁜 쪽 → 2. 노출도가 높은 쪽 → 3. 슬롯에 가까운 쪽 → 4. `MemberIndex` 낮은 쪽
- **분대 밖 경쟁**은 soft-claim이 못 본다 [A]. 그건 SmartObject 예약이 처리한다.
  즉 **soft-claim은 최적화이지 정확성 장치가 아니다** — 실패해도 시스템은 옳게 동작한다

**L1이 하는 일은 "보관"뿐이다** [A]. 점수 계산도 EQS 발행도 L1이 하지 않는다 (7.3절 금지 규칙).

### 6.2 표적 — 과집중 억제와 집중 지시 【신규】 [B]

같은 표적을 여러 명이 원하는 것은 **원칙적으로 정상**이다. 문제는 **전원이 한 명을 쏘는 동안
다른 적이 자유로운 것**이다.

```
표적 선택 축 배수 = 1 / (1 + FocusDecay × EngagedCount(T))      // FocusDecay = 0.6 [B]
                  × (T == FocusTarget ? FocusBonus : 1.0)        // FocusBonus = 2.0 [B]
```

- `EngagedCount`는 분대 틱마다 개인 상태(`FSoldierSquadStatus::CurrentTarget`)를 세어 갱신 [A].
  개인이 표적을 바꿀 때마다 L1에 통보할 필요가 없다 — **pull**이므로 (7.3절)
- 2명이 붙으면 배수 0.45, 3명이면 0.36 → 세 번째부터는 웬만해선 다른 표적이 이긴다 [B]
- `FocusTarget`이 걸리면 배수가 2배로 뛰어 **억제를 이긴다** — 4.3절의 "지시가 있으면 집중"

### 6.3 토큰 — 설계가 비워둔 발급·회수 규칙 【신규】 [B]

설계 9.5·상위계획 6.2절은 **토큰의 존재와 효과**만 정했다. 다음이 비어 있다:
*누구에게 주는가 / 언제 뺏는가 / 못 받은 사람은 굶지 않는가.*

**초기 상한** [B] — 분대 규모에 비례. 상위계획 [C-17]이 이 항목이다:

| 플랜 | 제압 토큰 | 이동 토큰 | 단위 |
|---|---|---|---|
| `Hold` | 0 | `ceil(N/2)` | 개인 |
| `BaseOfFire` | `ceil(N/2)` | 1 | 개인 |
| `Suppress` 명령 | `ceil(N×0.7)` | 1 | 개인 |
| `BoundingOverwatch` | `ceil(N/2)` | **조 1개** | **조** |
| `Flank` | `ceil(N/2)` (고정조에만) | **조 1개** (기동조 고정 보유) | **조** |
| `Withdraw` | `floor(N/3)` | **조 1개** | **조** |
| `Regroup` / `FormationMove` | 0 | N (전원) | 개인 |

**발급 우선순위** [B] — 요청 큐를 점수순으로:

```
Priority = RoleWeight(Role, TokenType)          // 지원화기수 × 제압토큰 = 1.5
         × HealthFactor                          // Injured면 이동토큰 우선, 제압토큰 후순위
         + StarvationBonus × 대기시간             // ★ 굶주림 방지
```

- **`StarvationBonus`가 없으면 특정 병사가 영구히 토큰을 못 받는다** [A] — 점수 기반 배분의
  고전적 실패다. 대기 1초당 +0.2 [B]
- **최소 보유시간** 1.5초 [B]: 받자마자 뺏기면 아무 일도 못 한다
- **최대 보유시간** [B]: `Suppression` 6초 / `Movement` 8초. **이게 없으면 교대가 안 난다** —
  한 명이 계속 쥐고 있으면 바운딩도 제압 순환도 멈춘다. 설계 9.5절의 "제압 토큰 **순환**"이
  이 한 줄에 달려 있다
- **즉시 회수 조건**: 사망/기절 / 탄약 0 / 플랜 전환 / 배역 변경

**StateTree와의 배선** — ★ 여기가 설계 규칙이 그대로 먹는 지점 【설계 상위계획 14.3·14.5】 [A]:

> "자원(슬롯 예약·토큰)은 **그것을 보유하는 상태가 부모**여야 한다. 해제를 상태 종료에 위임"

```
ST_Intent_Advance
 ├ AcquireMovementToken           tasks: STT_AcquireSquadToken(Movement)   ← 부모가 토큰 보유
 │   └ Bound                      tasks: STT_MoveTo(Assignment.Anchor), STT_SetSoldierInputState
 └ Overwatch  (토큰 실패 시 형제)  tasks: STT_SetWeaponPosture(ADS), STT_ScanSector
```

`EnterState`에서 획득 시도 → 실패면 `Failed` 반환 → 형제 `Overwatch`로 전이.
`ExitState`에서 **무조건 반납** → 사망·중단·상위 인터럽트 어느 경로로 나가도 누수가 없다.
설계가 SmartObject 예약 누수를 구조로 해결한 것과 **정확히 같은 장치**를 토큰에 재사용한다.

### 6.4 사격선(Fire Lane) 회피 【설계 9.5 "사격선에 아군" 확장】 [B]

설계는 이것을 **개인 유틸리티 축**("`AimedFire` 축으로 승격")으로만 다뤘다. 분대 차원에서 한 줄 더:

제압 토큰 보유자는 자기 사격선을 blackboard에 게시한다.
`FSquadFireLane{ Origin, Dir, HalfWidthCm=150 }`. 기동조는 **경로 생성 시 lane을 비용 페널티로**
반영한다(NavMesh 쿼리 필터 또는 EQS 테스트로).

- lane 개수 상한 = 제압 토큰 수 → 최대 3~4개. 비용 무시 가능 [B]
- **금지선이 아니라 비용이다** [A]. 우회로가 없으면 지나가되, 그때 사격자 쪽 개인 축이
  사격을 멈춘다 — 이중 안전

## 7. 성능 — 45명 @ 60fps

### 7.1 예산과 규모 【설계 12.1~12.2】 [A]

| 항목 | 값 |
|---|---|
| 동시 병사 | 45명 (아군 30 + 적 15) |
| **분대 조율 예산** | **0.1 ms / frame** (AI+애님 5.0ms 중) |
| 분대 틱 주기 | 2~4 Hz |
| 분대 수 [B] | 45 / 4~6명 = **8 ~ 11개** |

**산술** [B]: 11분대 × 3Hz = **33 분대틱/초**. 60fps면 **프레임당 0.55회**.
즉 예산 0.1ms는 "분대 틱 1회당 **약 0.18ms**"를 뜻한다 — 평균이 아니라 **1회 비용의 상한**이다.

### 7.2 스케줄링 — 프레임당 최대 1분대 【신규】 [B]

```
USquadSubsystem::Tick()
  Accumulator += DeltaTime × (SquadCount × SquadTickHz)
  while (Accumulator >= 1.0 && ProcessedThisFrame < MaxSquadsPerFrame)   // MaxSquadsPerFrame = 1
      Squads[Cursor++ % SquadCount].TickSquad()
      Accumulator -= 1.0
  Accumulator = min(Accumulator, MaxAccumulator)     // 1.0 — 밀린 것을 몰아치지 않는다
```

- **`MaxSquadsPerFrame = 1`이 스파이크 방어선이다** [A]. 이게 없으면 힛치 후 복귀 프레임에서
  11개 분대가 한꺼번에 돈다
- **`MaxAccumulator` 클램프**가 없으면 위와 같다. 밀린 분대 틱은 **버린다** — 분대 결정은
  2~4Hz면 충분하므로 한두 번 건너뛰어도 무해하다 [B]
- 커서 라운드로빈이므로 **분대 간 스태거링이 공짜**로 나온다

### 7.3 ★ 분대 틱이 **절대 하지 않는 것** 【신규】 [A]

> **이 표가 0.1ms 예산을 지키는 실제 장치다.** 나머지는 전부 산술이고, 예산이 터지는 것은
> 항상 "분대가 편해서 여기서 트레이스 한 번 쏘자"에서 시작한다.

| 금지 | 대신 |
|---|---|
| **라인 트레이스 / 스윕** | 개인 인지가 이미 한 결과(`FSoldierSquadStatus`)를 읽는다 |
| **EQS 질의 발행** | 개인 L3가 발행한 결과의 **soft-claim만 보관**(6.1절) |
| **경로 재계산** | 회랑/집결점 검증 시 **플랜 전환당 비동기 1회**만 (4.2절) |
| **멤버별 LoS 계산** | 개인이 계산한 스칼라를 읽는다 |
| **개인 기억 순회** | 개인이 **보고한 것**만 본다(5절) |
| **매 틱 조 재편성** | 플랜 전환 시에만 (2.3절) |

**허용되는 것은 사실상 넷뿐이다**: 캐시된 스칼라 읽기 / O(N) 벡터 합 / O(8) 위협 정렬 / 큐 pop.

### 7.4 분대 틱 3-페이즈 분해 【신규】 [B]

한 번의 분대 틱에서 전부 하지 않는다. 비싼 것을 뒤로 미룬다.

| 페이즈 | 주기 | 내용 | 비용 형태 |
|---|---|---|---|
| **A · 수집·유지** | 매 분대 틱 (3Hz) | 멤버 상태 pull, centroid/분산도, 사기 갱신, 토큰 회수·발급, 보고 큐 pop, `EngagedCount` 집계 | O(N) + O(큐) |
| **B · 플랜 재평가** | **0.5Hz** 또는 이벤트 | 플랜 스코어링, 조 편성, 배역 배분 | O(플랜 수 × 게이트) |
| **C · 공간 준비** | **플랜 전환 시 1회** | 회랑 생성·검증, 집결점, bound line, 대형 슬롯 | NavMesh 투영 1 + 비동기 경로 1 |

**페이즈 B를 깨우는 이벤트** [B]: 새 명령 도착 / 사상자 발생 / 접촉 시작·종료 /
사기 임계 통과 / 분대장 사망. — **이벤트가 있으므로 0.5Hz가 굼뜨지 않다.**

## 8. StateTree와 어떻게 물리는가

### 8.1 분대는 StateTree를 쓰지 않는다 【신규】 [B]

| 근거 | |
|---|---|
| 1 | 분대 결정은 **상태 기계가 아니라 스코어 선택**이다 (설계 9.2 "계획기 없이 스코어 기반 선택"). StateTree에 넣으면 설계 8.1절이 BT를 배제한 이유("우선순위가 트리 구조에 하드코딩")가 L1에서 재발한다 |
| 2 | **[C-13] StateTree 인스턴스 비용 × 45명**이 아직 미측정이다. 분대 11개가 더 얹히면 미지수가 커진다 |
| 3 | 분대 로직은 **디버그 HUD로 보는 것**이 자연스럽다(상위계획 10절: 플랜/토큰/사기 게이지). StateTree 디버거는 상태 전이를 보는 도구지 배분 현황을 보는 도구가 아니다 |

**재검토 조건** [A]: 분대 플랜이 "다단계 순차 절차"(문 개방 → 진입 → 방 정리)를 갖게 되면
그때는 StateTree가 맞다. 설계 13절이 HTN 재검토 조건으로 든 것과 **같은 신호**다.

### 8.2 개인 StateTree가 분대를 읽는 경로 — Evaluator 【설계 상위계획 R4 해결】 [B]

GASP `STE_GetAIData` 패턴을 그대로 승계한다.

```
FSTE_SquadContext : FStateTreeEvaluatorCommonBase
  Input  : AIController (Context)
  Output : FSquadAssignment Assignment      ← 조건·태스크가 데이터 바인딩으로 읽는다
           bool             bHasSquad
           uint32           AssignmentRevision
```

- 매 틱 `USquadSubsystem::FindSquadFor(Pawn)` → `GetAssignment(MemberIndex)` **복사 1회**.
  분대 배정은 3Hz로만 바뀌므로 `Revision`이 같으면 복사도 건너뛴다 [B]
- **Evaluator 하나로 통일한다** [A] — 태스크마다 각자 분대를 찾으면 룩업이 태스크 수만큼 늘고,
  같은 틱 안에서 배정이 달라 보이는 사고가 난다

### 8.3 신규 노드 목록 【설계 상위계획 4.2 표에 이미 예고된 것 포함】

| 노드 | 종류 | 출처 | 하는 일 |
|---|---|---|---|
| `FSTE_SquadContext` | Evaluator | 【신규】(R4 패턴) | 배정 노출 |
| `FSTT_AcquireSquadToken` | Task | 【설계】4.2 `STT_AcquireToken` | 획득/보유/**ExitState 반납** |
| `FSTT_ReportSlotClaim` | Task | 【신규】6.1 | soft-claim 등록/해제 |
| `FSTC_SquadHasToken` | Condition | 【신규】 | 전이 게이트 |
| `FSTC_SquadTaskIs` | Condition | 【신규】 | 배역별 분기 |
| `FSTC_IsInsideCorridor` | Condition | 【신규】4.2 | 회랑 이탈 감지 |

**C++로 만드는 이유** [B]: 토큰은 **결정론과 서버 게이트**가 중요하고 매 상태 진입마다 돈다.
GASP의 기존 태스크가 BP인 것과 섞여도 무방하다(같은 StateTree에서 공존).
얇은 것(`SetSoldierInputState` 등)은 지금처럼 BP로 둔다.

> ⚠ **[C-63]** C++ StateTree 노드 베이스 클래스명·헤더 경로는 UE5.8 엔진 소스에서
> **반드시 대조할 것.** 이 초안은 5.3~5.5 계열 API(`FStateTreeTaskCommonBase` /
> `FStateTreeConditionCommonBase` / `FStateTreeEvaluatorCommonBase` + `FInstanceDataType`)를
> 가정했고 **컴파일 검증하지 않았다.** 또한 노드가 `UStateTreeAIComponentSchema`에서
> 보이려면 스키마의 허용 규칙을 통과해야 한다.

### 8.4 서브트리 배선 예 — 설계 4.1절 목록에 분대가 얹히는 모습 [B]

```
ST_Intent_Advance                              ← LinkedAsset (설계 상위계획 13.1)
 ├ [cond] FSTC_SquadTaskIs(Bound)
 │   └ AcquireMovementToken   task: FSTT_AcquireSquadToken(Movement)   ← 부모 = 자원 보유
 │       └ MoveToBoundLine    tasks: StateTreeMoveToTask(Assignment.Anchor),
 │                                   STT_SetSoldierInputState(Gait=Run, Aim=true)
 └ [cond] FSTC_SquadTaskIs(Overwatch)
     └ HoldOverwatch          tasks: STT_SetWeaponPosture(ADS), STT_ScanSector(SectorYawRange)
```

토큰 획득 실패 → `MoveToBoundLine` 진입 불가 → 자동으로 엄호. **분기 로직을 쓰지 않았다.**
