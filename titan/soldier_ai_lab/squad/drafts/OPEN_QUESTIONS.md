## 🔴 지금 답이 필요한 것 (S0 착수 전)

### Q24 · 분대 표준 규모는 몇 명인가

| | |
|---|---|
| **왜 지금인가** | 토큰 상한 공식(`ceil(N/2)` 등), 조 편성 규칙, 분대 수 → **성능 산술 전체**가 여기 딸린다. 나중에 바꾸면 6.3절 표를 전부 다시 잡아야 한다 |
| **선택지** | (a) **4명** — 조 2×2. 미군 fireteam. 교대가 빠르고 토큰 산술이 깔끔 <br> (b) **5명** — 조 3+2. `PLAN.md` 전반의 기본 가정 <br> (c) **6명** — 조 3×3. 화력 여유, 대신 45명이 7~8분대로 줄어 분대당 계산이 커진다 |
| **내 권고** | **(b) 5명.** 설계 14절 P2 검수 기준이 **"5명 vs 5명"** 이라 검수와 구현이 같은 수를 쓴다. 3+2 비대칭은 오히려 "누가 먼저 뛰나"를 자연스럽게 만든다 |
| **영향 없는 것** | 코드 구조. 전부 데이터(`FSquadDefinition`)라 값만 바꾸면 된다 |

### Q25 · 45명을 어떻게 분대로 나누는가

| | |
|---|---|
| **왜 지금인가** | 설계 12.1절이 **아군 30 + 적 15**로 못박았다. 5명 분대면 아군 6개 + 적 3개 = **9분대**. 이 수가 성능 예산 산술의 분모다 |
| **질문** | ① 아군 30명이 정말 전부 분대에 속하는가, 아니면 일부는 분대 없이(호위·고정 배치) 도는가?<br> ② 적 15명이 3개 분대인가, 아니면 더 잘게 쪼개 5개 소조인가? |
| **내 권고** | 아군 6분대 + 적 3분대 = **9분대**. 분대 없는 병사도 지원한다(`FSTE_SquadContext`가 `bHasSquad=false`를 정상 처리) |
| **주의** | 분대를 잘게 쪼갤수록 분대 수가 늘어 **총 분대 틱 비용이 선형으로 오른다.** 15명을 5개 소조로 하면 총 11분대가 되고 예산이 22% 빡빡해진다 |

### Q28 · 분대 편제를 어디에 저작하는가 (= D11)

| | |
|---|---|
| **선택지** | (a) **DataTable** (`FSquadDefinition`) + 레벨의 병사에 `SpawnTag` — 초안이 가정한 방식 <br> (b) **레벨에 `ASquadCoordinator`를 직접 배치**하고 병사를 드래그로 연결 <br> (c) **스포너 액터**가 분대와 병사를 함께 생성 |

| **결정이 필요한 이유** | 셋 다 코드가 다르다. 나중에 바꾸면 S0 을 다시 짠다 |

## 🔴 다른 담당자와 합의가 필요한 것

### Q23 · 인지 담당자와 `ISoldierThreatMemorySink` 계약

**내가 요구하는 것**(`PLAN.md` 5.3절 · `SquadTypes.h`):

```cpp
ISoldierThreatMemorySink::ReceiveSharedThreat(const FSharedThreat& Report)
```

수신 측이 지켜야 하는 규칙 3개:

| # | 규칙 | 안 지키면 |
|---|---|---|
| R1 | 직접 목격이 더 최신이면 이 보고를 **버린다**. 절대 덮어쓰지 않는다 | 남의 낡은 무전이 내 방금 목격을 지운다. 병사가 방금 본 적을 놓친다 |
| R2 | 이미 공유로 알던 것보다 오래된 보고는 버린다 | 지연 배달 순서가 뒤집히면 정보가 거꾸로 간다 |
| R3 | 병합 결과 `Confidence` ≤ 0.6 (설계 9.3절 상한) | 들은 것이 본 것과 같아진다 = 치팅으로 보인다 |

**그리고 결정이 필요한 것**: `FThreatMemory`(설계 7.4절)에 **`LocationSigmaCm` 필드를 추가할
것인가?**

- **추가한다면**: 개인이 σ를 들고 있으므로 조준 억제(σ > 400cm면 정조준 불가)가 인지·조준
  쪽에서 자연스럽게 걸린다. **이쪽을 권고한다** — `PLAN.md` 5.2절 모델의 핵심이 σ이고,
  σ가 개인 기억에 없으면 "들은 적을 정조준하지 않는다"를 구현할 자리가 없다.
- **추가하지 않는다면**: `bSharedBySquad` 플래그만으로 이분법 처리(공유면 무조건 조준 금지).
  단순하지만 "가까이서 방금 알려준 것"과 "멀리서 10초 전에 알려준 것"이 같아진다.

### Q29 · 엄폐 담당자와 슬롯 식별자 타입

`FSlotSoftClaim::SlotId`를 `FGuid`로 잡았다. 엄폐 담당자가 SmartObject 슬롯을
`FSmartObjectSlotHandle` / `FSmartObjectClaimHandle` 로 다룬다면 **그 타입으로 맞춰야 한다.**

또한 중재 훅의 삽입 지점 합의가 필요하다:

```cpp
USquadComponent::GetSlotContentionMultiplier(MemberIndex, SlotId) -> float
```

- 이것을 **EQS 커스텀 Test** 로 넣을 것인가, 아니면 L3가 EQS 결과를 받은 뒤 후처리로 곱할 것인가?
- **내 권고**: EQS Test. 상위 N개 가중 랜덤 선택(설계 10.5절)이 **감점 후 점수**로 이루어져야
  의미가 있다. 후처리로 곱하면 이미 순위가 정해진 뒤라 효과가 반감된다.

## 🟡 해당 단계에서 답이 필요한 것

### Q26 · 편제 역할 6종이 맞는가

초안: `Rifleman / Leader / AutomaticRifleman / Grenadier / Marksman / Medic`

**진짜 질문은 "역할이 몇 개인가"가 아니라 "역할이 실제로 다르게 행동하는가"** 이다.
`PLAN.md` 2.2절이 정한 대로 역할은 **가중치로만** 작동하므로, 다음 중 하나라도 없으면
그 역할은 `Rifleman`과 구별되지 않는다:

| 역할 | 구별되려면 필요한 것 | 현재 SoldierLab 에 있나 |
|---|---|---|
| `AutomaticRifleman` | 제압 토큰 우선 + 다른 무기 | 무기 데이터 없음 |
| `Grenadier` | `Grenade` Intent (설계 8.3절에서 **2차**로 표기) | 없음 |
| `Marksman` | 장거리 조준 프로파일 | 없음 |
| `Medic` | `Revive`/`Assist` Intent (설계 8.3절 **2차**) | 없음 |

**권고**: **P2 단계에서는 `Leader` / `Rifleman` / `AutomaticRifleman` 3종만** 쓴다.
나머지 3종은 enum 에 자리만 남기고 데이터를 만들지 않는다. 지금 6종을 다 만들면
**차이가 없는 역할이 6개 생기고, 그게 있다는 이유로 나중에 유지보수 대상이 된다.**

### Q30 · `Suppress` 명령이 별도 플랜이어야 하는가

초안은 `Suppress` = `BaseOfFire` + **제압 토큰 상한만 올린 것**으로 처리했다(`PLAN.md` 3.3절).

- **찬성 근거**: 플랜을 하나 덜 만든다. 실제로 하는 일이 "더 많이 쏜다"뿐이다.
- **반대 근거**: "제압"은 명중이 아니라 **탄착을 특정 구역에 유지하는 것**이라 조준 방식이
  다르다. 이걸 개인 축으로만 표현할 수 있는지는 사격 담당 범위다.

**권고**: 지금은 토큰 설정 차이로 두고, P2 관찰 후 재검토. 결정을 미룰 수 있는 항목이다.

### Q31 · 사기가 **개인**에게 얼마나 새어나가야 하는가

설계 9.4절: "임계 이하 → 플랜이 `Withdraw`로, **개인의 `Retreat` 축도 함께 상승**".

문제: **분대 사기와 개인 판단이 같은 방향으로 두 번 작용한다.** 사기가 떨어지면
① 플랜이 Withdraw 로 바뀌고 ② 개인 Retreat 점수도 오른다 → **과반응**이 나올 수 있다
(전원이 동시에 도망).

| 선택지 | |
|---|---|
| (a) 초안대로 둘 다 | 설계 그대로. 단 개인 축 가중치를 낮게 잡아야 한다 |
| (b) 분대 사기는 **플랜만** 바꾸고 개인 축에는 안 넣는다 | 후퇴가 **조 단위 교대**로만 일어난다. 더 "훈련된" 느낌 |
| (c) 분대장 생존 시 (b), 분대장 사망 시 (a) | 지휘가 무너지면 각자도생 — 연출로는 가장 좋다 |

**권고**: **(b)로 시작.** 설계가 (a)를 적었지만, 개인 유틸리티 축은 아직 튜닝 전이라
[C-14]와 얽혀 이중 튜닝이 된다. (c)는 P2 이후 여유가 있으면.

### Q32 · 분대장 사망 시 사기 페널티 (= D12)

승계는 구현했으나 **페널티를 줄지 안 줄지**를 정하지 않았다. 설계 9.4절 공식에는
`+ 분대장 생존 × w5`가 있어 **이미 보너스가 사라지는 형태로 반영**된다(w5=0.15).
추가 페널티를 더 줄 것인가?

**권고**: 주지 않는다. 보너스 소멸만으로 0.15 하락이고, 사상자 페널티(0.18)도 동시에 걸려
합계 0.33이 한 번에 빠진다. 그 이상은 과하다.

## 🟢 방향만 정해두면 되는 것

### Q27 · 분대 로직을 StateTree 로 갈 여지를 남길 것인가

초안은 **분대에 StateTree 를 쓰지 않는다**(`PLAN.md` 8.1절). 근거 3개와 재검토 조건을
함께 적어두었다.

- 지금 결정할 필요는 없다. **다만 "분대도 StateTree 로 해야 하지 않나"라는 질문이
  나중에 반복될 것**이므로, 근거를 문서에 남겨둔 것이다.
- 재검토 신호: 분대 플랜이 **다단계 순차 절차**(문 개방 → 진입 → 방 정리)를 갖게 될 때.
  설계 13절이 HTN 재검토 조건으로 든 것과 같은 신호다.

### D10 · 분대가 2명으로 줄면 합칠 것인가

설계 [C-16]("분대 동적 생성 vs 사전 배정")의 나머지 절반이다. 초안은 **사전 배정 고정**이고
합치지 않는다.

- 합치면 Days Gone 방식에 가까워지고 후반 전투가 덜 초라해진다.
- 대신 `FSquadHandle` 재배정, 토큰 이관, 조 재편성이 전부 필요해진다 — **구조가 눈에 띄게 는다.**

**권고**: P2 에서는 하지 않는다. 대신 **생존자 2명 이하 분대는 `Regroup`/`Withdraw` 로 강제**해서
"소멸한 분대가 어색하게 공격하는" 장면만 막는다. 합병은 P3 이후 재검토.

### Q33 · `EOrderRecipientType::Individual` 의 의미 (= 설계 D7)

내 범위에 걸린다: **개인 직접 명령이 L1을 우회하는가?**

| 선택지 | 결과 |
|---|---|
| (a) 우회한다 (L0 → 개인) | 시나리오 저작이 편하다. 대신 분대가 모르는 사이 한 명이 사라져 토큰·조 편성이 어긋난다 |
| (b) 분대가 중계한다 (L0 → L1 → 개인) | 분대가 "이 사람은 지금 별도 임무"를 알고 배역에서 뺀다. **일관성이 유지된다** |

**권고**: **(b).** `FSquadAssignment::Task` 에 `Detached` 같은 값을 하나 더 두고, 그 멤버를
토큰·조 편성에서 제외한다. (a)를 택하면 "분대는 5명인 줄 아는데 실제로 4명"인 상태가 생긴다.
P3 항목이므로 지금 구현하지 않는다.

## 부록 · 이 초안에서 내가 **설계를 수정한** 곳 (승인 필요)

설계 문서를 따르라는 지시를 받았으므로, **설계와 어긋나게 쓴 곳을 전부 명시**한다.

| # | 설계 서술 | 내가 쓴 것 | 왜 |
|---|---|---|---|
| 1 | 9.5·상위계획 6.2: "**이동 토큰만으로 바운딩 오버워치가 창발한다. 별도 로직이 필요 없다**" | 이동 토큰을 **조 단위**로 발급하는 플랜을 따로 뒀다 | 개인 단위 발급에서는 매 틱 다른 2명이 토큰을 잡아 **산개 전진**이 나오고, 조 교대가 절대 안 생긴다. `PLAN.md` 4.1절에 반례를 적었다. **원문의 "별도 로직 불필요"는 개인 단위 재배치(BaseOfFire)에서는 그대로 맞다** |
| 2 | 3.7: `Squad/ USquadComponent` | `ASquadCoordinator`(AInfo) 호스트를 추가 | 분대장 폰에 붙이면 분대장 사망 시 분대 상태가 함께 파괴된다. 설계 9.5절의 "차순위 승계"와 충돌한다 |
| 3 | 9.2: 플랜 6종 | 7종 (`FormationMove` 추가) | 설계 11.3절이 "`Verb=Advance` + 접촉 없음 → **대형 이동**"이라고 적었는데 그 플랜에 이름이 없었다. 이름만 붙였다 |
| 4 | 9.3: 공유 위협 = `Confidence 0.6` | + 지연 큐 + `LocationSigmaCm` | 설계는 "얼마나 믿는가"만 정했고 "언제 아는가 / 얼마나 정확히 아는가"가 비어 있었다. 그 둘이 치팅 인상의 실제 원인이다 |
| 5 | 9.4: 사기 공식 | + EMA 평활화 | 원식은 순간값이라 사기가 튀고 플랜이 요동친다 |
| 6 | 11.2: `EOrderVerb::HoldFire` | 플랜을 바꾸지 않는 특수 동사로 격리 | 설계 11.2절 주석도 "교전규칙만 바꿈"이라 적었으나, 11.3절의 Verb→플랜 경로에 넣으면 진형이 풀린다 |
| 7 | 9.5: SmartObject 예약이 중복 선점을 해결 | + soft-claim 사전 예고 | 예약은 경쟁 **결과**만 준다. 둘이 같은 슬롯으로 개활지를 가로질러 뛰는 것은 못 막는다. **다만 soft-claim 은 최적화이지 정확성 장치가 아니다** — 실패해도 시스템은 옳게 동작한다 |

**1번과 4번이 가장 중요하다.** 나머지는 이름 붙이기·보강 수준이다.
