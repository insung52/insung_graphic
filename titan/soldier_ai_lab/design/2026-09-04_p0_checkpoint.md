## 2. 달라진 것 — 7가지

### 2.1 ★ 리스크 장부가 통째로 뒤집혔다

| | 계획 | 실제 |
|---|---|---|
| `Enable_Warping` | **최대 리스크.** 자체 제작 필요 추정 | **공짜.** GASP `AM_WarpingAlpha`가 이미 생성기 |
| `contact_l/r` | "`MotionExtractor`로 뽑으면 됨" | **이진 사각파.** 엔진 기본 모디파이어로 불가 → **C++ 모듈 신설** |

`CURRENT_STATE` 7절 리스크 표의 1순위와, 사실상 언급도 없던 항목이 **자리를 맞바꿨다.**

### 2.2 인플레이스 전제가 틀렸다

`assets/...` 4.2절 [1]단계가 "무료 **인플레이스** 클립 확보"였다. `EncodeRootBoneModifier`는
**이미 있는 이동을 루트로 재배치**할 뿐 없는 이동을 만들지 않는다(엔진 소스 확인).
→ 조달 지시가 정반대로 바뀌었다. 14절에 정정.

### 2.3 커브는 "필수 N종"이 아니라 클립 종류별 세트

P8 규칙을 **하루에 두 번 다시 썼다**: 3종 → 5종 → **종류별 세트**.
Epic은 워핑을 못 쓰는 동작에 커브를 0으로 채우는 게 아니라 **아예 안 만든다.**
표본이 Walk 폴더에 치우쳐 있어 두 번째 판단도 틀렸다.

### 2.4 P0-1은 "만드는 일"이 아니라 "확인하는 일"이었다

GASP에 AI 스택이 통째로 있었다(`AIC_NPC_SmartObject` + StateTree 3종 + 태스크 6종).
`STT_SetCharacterInputState`가 **플레이어와 같은 인터페이스**로 input state를 채운다.
우리가 실제로 만든 것은 **5개 축을 노출하는 태스크 하나**뿐이다.

계획은 "2~3일 배선 작업"이었는데 **배선은 이미 돼 있었고**, 우리 몫은 GASP가 안 채우는
4개 축(`wantsToAim`/`Crouch`/`Strafe`/`Sprint`)을 여는 것이었다.

### 2.5 설계 문서에 없던 축이 튀어나왔다 — CMC vs Mover

GASP는 캐릭터가 **두 벌**이고 DB 세트도 갈린다. 설계 3.1절은 CMC를 전제했지만
**AI 예제가 Mover에도 붙어 있어** 선택 문제가 됐다(**[Q11]**).
→ CMC 확정. 다행히 두 캐릭터가 같은 인터페이스를 구현해 **이관 비용 0**이었고,
`NPCLevel`에 CMC 3기가 이미 배치돼 있었다.

이건 "틀린 것"이 아니라 **설계 시점에 몰랐던 축**이다. `[U6]`(Relaxed 티어의 성격)이
여기서 같이 풀렸다 — LOD가 아니라 Mover 경로의 DB 세트였다.

### 2.6 계획에 없던 구조 변경 — C++ 에디터 모듈

`Source/SoldierLabEditor/` 신설. `UFootContactCurveModifier` 때문이다.
**부작용**: 이제 새 PC/클린 클론에서 **C++ 빌드가 선택이 아니라 필수**다(`CLAUDE.md` 7절 보강).

### 2.7 MCP 능력의 경계를 여러 번 잘못 적었다

| 항목 | 처음 기록 | 실제 |

## 3. 반복된 실패 패턴

**이번 세션에서 뒤집힌 것 전부가 [B](잠정) 또는 무표기 항목이었다. [A](확정) 항목은 하나도 안 뒤집혔다.**

`CLAUDE.md` 3.1절이 "이 프로젝트 초기에 확인하지 않은 것을 세밀하게 쓴 항목이 네 번 틀렸다"고
적어놨는데, **같은 종류가 이번에 네 번 더 나왔다**(2.1~2.4). 신뢰도 표기 규칙은 작동하고 있다 —
문제는 **[B]를 [A]처럼 읽고 그 위에 계획을 세운 것**이다.

### 이번에 효과가 컸던 대응 두 가지

1. **계측 먼저** — 접지 임계값을 추측으로 세 번 고치다 `UE_LOG`로 분포를 찍자 원인이 한 번에
   드러났다 → `CLAUDE.md` **P10**으로 규칙화
2. **GASP 실물 대조** — "이래야 한다"는 예상이 여러 번 틀렸고, 매번 GASP 에셋을 실측해
   바로잡았다. 특히 **"우리 클립을 GASP 클립과 같은 상태로 만든다"** 는 판정 기준이 명확했다

## 4. 그래서 남은 계획을 어떻게 조정하나

### 4.1 순서는 유지한다

①②③ 순서가 옳았다. ③에서 ④(P0-2)로 가는 흐름도 그대로.

### 4.2 P0-2의 성격이 바뀐다

계획: "워핑 각도 한계가 아니라 **전환 데이터 없이 견착 이동이 얼마나 버티는가**"

이제 여기에 **선행 조건이 하나 붙는다** — 견착 클립을 재생시키려면
**ABP/챙터 배선**(`rotationMode == Aim` → 우리 DB)이 필요하다. 클립을 DB에 넣어도
챙터가 안 가리키면 안 뽑힌다. 이건 계획에 없던 작업량이다.

### 4.3 데이터가 병목이라는 것이 확정됐다

축(`wantsToAim` → `rotationMode = Aim`)은 GASP에 **이미 다 있다.**
`AddTarget`/`RemoveTarget`, `Get_PropertiesForAnimation` 같은 L3↔L4 계약도 이미 있다.
→ **우리가 만들 것은 시스템이 아니라 데이터와 얇은 배선이다.**
`CURRENT_STATE` 3.4절("조달 요청의 성격이 바뀌었다")이 세 번째로 재확인됐다.
