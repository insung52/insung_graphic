## 1. ★ 노출의 사다리 — 조리개와 자세 [A]

### 1.1 막힘의 답은 거절이 아니라 **다른 총구 위치**다 (P81)

`..._engagement_and_cover.md` 3.1절이 세운 기구는 그대로다 — **사선은 총구에서 쏘고,
총구는 자세를 따라 내려간다.** 그래서 낮은 담 뒤에 웅크린 병사의 총열은 담 아래고
사격은 거절된다. 여기까지가 원본이다.

**그런데 그것이 병사가 할 수 있는 전부는 아니다.** 사람은 막힌 사선 앞에서 포기하지 않고
**총을 다른 데로 옮긴다.** 컴포넌트는 이제 **다른 총구 위치에서 같은 사선 트레이스를
다시 쏴서** 뚫리는 자리를 찾는다.

```
Direct   지금 그대로. 아무 재주도 필요 없다
Over     기립 높이로 올린 총구            ← 낮은 담
Right    액터 오른쪽으로 LateralReachCm   ← 모서리
Left     반대쪽
None     어느 배치로도 안 뚫린다          → FireIntent = Blocked
```

**순서가 뜻을 갖는다.**

- **가장 싼 사격은 아무 재주도 안 쓰는 사격**이므로 `Direct` 가 먼저다
- **`Over` 가 옆보다 먼저다.** 낮은 담은 *돌아가는* 것이 아니라 *넘어서* 쏘는 것이고,
  일어서는 데는 **발을 옮길 필요가 없다.** 모서리이면서 동시에 낮기도 한 엄폐물은
  넘어서 쏘는 것이 맞다

### 1.2 ★ 기하가 주는 두 답이 **이미 있던 두 축**이다

조리개의 답은 **위** 아니면 **옆**이다. 그런데 포즈 파이프라인의 블라인드 파이어 축도
**`BlindFireV`(위)** 와 **`BlindFireH`(좌우)** 둘이다(`IMPLEMENTED.md` 2.5e절).

**맞춰 놓은 것이 아니다.** 물체를 지나가는 방법이 위와 옆뿐이기 때문에 양쪽에서 같은 둘이
나왔을 뿐이다. **[W19]**("린·블라인드 파이어 축을 AI가 몰지 않는다 — 다리는 이미 놓여 있다")가
**새 판단 재료를 하나도 만들지 않고** 닫힌 것이 이 때문이다.

### 1.3 나갈 구멍을 찾았으면, **몸을 얼마나 내보낼지**를 고른다

```
Open    일어서서 정면으로.      노출 전부, 정확도 전부
Lean    어깨만 모서리 밖으로.   LeanSpreadScale  1.4
Blind   총만.                   BlindSpreadScale 4.0
```

**어느 칸에 설지는 제압(suppression)이 정한다.** 제압은 **지금 이 순간 노출의 값이
얼마인가**를 재는 양이고, 그것이 바로 이 결정에 필요한 것이기 때문이다.

```
bTooDearToShow = Suppression >= SuppressionToGoBlind 0.45
               || 거리 <= BlindFireCloseRangeCm 400
```

- **아무도 안 쏘는 병사는 일어서서 조준한다**
- **집중 사격을 받는 병사는 총만 담 위로 올린다**
- **4m 안의 표적에게도 총만 내민다** — 그만큼 가까운 자는 **볼 값어치가 없다**

둘 다 어디에도 규칙으로 쓰여 있지 않다. **탄 한 발의 값과 몸을 보이는 값의 비교 하나**다.

### 1.4 ★ `Over` 로 쏘기로 한 순간, **엄폐 층의 요구를 덮는다**

```cpp
case ESoldierAperture::Over:
    ...
    Posture = ESoldierFiringPosture::Open;
    DesiredStance = 0.f;        // 엄폐가 요구한 자세를 덮어쓴다
```

**일어선다는 것이 곧 드러나기로 한 결정 그 자체**다. 그것을 엄폐 층의 "낮게 있으라"는
요구 뒤에 숨기면 **거래가 일어났다는 사실이 안 보인다** — 병사는 일어서지도 쏘지도 못한 채
둘 사이에서 떨게 된다.

### 1.5 ★ 블라인드 파이어의 큰 벌점은 **밸런스 다이얼이 아니다**

`BlindSpreadScale 4.0` 은 "맹목사격을 약하게 만들자"가 아니다. 그 값은 **절대 가치
게이트**(2.2절)가 **먼 거리의 맹목사격을 거절하게 만드는 장치**다.

```
콘이 4배 → 탄착 반경 4배 → √(반경² + 탄착²) 이 SuppressiveRadiusCm 500 을 금방 넘는다
→ "쏠 값어치 없음" → 맹목사격은 가까운 상대에게만 남는다
```

**그리고 가까운 상대야말로 맹목사격이 맞는 답인 자리다.** "맹목사격은 근거리 전용"이라는
규칙을 쓰지 않고 나온 결과다.

### 1.6 ⚠ 한 가지 전제 [B]

좌우 조리개는 **액터의 right vector** 로 옆을 정한다 — 즉 **병사가 위협을 향하고 있다**는
전제다. 3절의 조준 선회가 들어오면서 **몸이 아직 안 돌아간 순간**이 생겼으므로,
선회 중에는 "옆"이 사선을 가로지르지 않을 수 있다. 지금은 `Traversing` 이 그 구간의
사격을 막고 있어 증상이 나오지 않는다 **(추정)**. → **[C-91]**

## 2. 이동 · 반동 · 절대 가치 게이트 [A]

### 2.1 이동은 이미 콘을 넓히고 있었다 (원본 4절)

```
EffectiveSpreadAtCm(d) = d × tan(3°) × (1 + MovementSpreadScale 2.0
                                            × min(1.5, 속도 / ReferenceSpeedCms 600))
```

### 2.2 ★ 절대 게이트 — 비율 게이트만으로는 안 된다 (P67, 원본 4절)

```
TotalErrorCm = √(RadiusCm² + SpreadCm²) ≤ SuppressiveRadiusCm 500
```

**앎↔무기 비교는 비율**이라 무기가 절망적인 병사도 자기 앎이 더 절망적인 한 계속 자격을
얻는다. **40m를 전력질주하며 탄창을 비우는** 거동이 정확히 그것이고, **담 위로 총만 흔드는
사격**도 같은 논리로 자격을 얻는다. 절대 게이트가 그 자리를 막는다.

**만들기 전에 계산한 교전 상한** (스태미나 시스템은 **관여하지 않는다** — 명시적 요구다):

| 이동 | 교전 상한 |
|---|---|
| 정지 | **95m** |
| 걷기 | **57m** |
| 조깅 | **32m** |
| 전력질주 | **24m** |

**근접전은 그대로 run-and-gun이다** — 5m에서는 전력질주 중의 콘도 폭이 1m 남짓이다.
→ **[C-86]** (여전히 플레이에서 재지 않았다)

### 2.3 ★ 반동 — **탄창이 줄어드는 것을 보고 발사를 센다** [W26 해결]

**새 훅을 만들지 않았다.** 무기는 이미 `SetWeaponState(탄/탄창/재장전중)` 으로 탄약을
보고하고 있고(`..._ai_bridge_and_scene.md` 5절), **탄이 줄었다는 것이 곧 한 발 쐈다는
것**이다.

```cpp
const bool bFiredThisTick = Ammo < LastAmmo;
```

```
RecoilPerShot            0.18   한 발이 더하는 콘 (기본 콘의 배수)
RecoilRecoveryPerSecond  1.2    안 쏘는 동안 초당 빠지는 양
MaxRecoilSpreadScale     2.5    상한
BlindRecoilScale         2.0    맹목사격일 때 상승률 2배
```

**맹목사격이 반동을 두 배로 먹는 이유**: 팔 끝으로 담 밖에 내민 총은 **눌러 둘 수가 없다.**
견착의 값이 바로 그것이다.

귀결 둘 — **제압 사격이 더 이상 공짜로 정확하지 않고**, 맹목사격의 "근거리 전용"이
1.5절의 기구와 겹쳐 **두 겹으로** 성립한다. → **[C-92]**

## 3. ★ 조준 선회와 `Traversing` 의도 [A]

### 3.1 증상 — **터렛처럼 돌았다**

조준은 `SetFocalPoint` 에 **접촉 위치를 그대로 넘기고** 있었다. 컨트롤 로테이션은
**즉시 설정되는 값**이고 몸통만 유한 각속도로 따라간다(`IMPLEMENTED.md` 2.5d절).
그래서 **표적을 바꾼 병사는 총구가 먼저 순간이동하고 발이 뒤늦게 따라왔다.**

### 3.2 고친 방법 — **무기가 실제로 도달한 각도**를 따로 들고 있는다

```cpp
AimRotation = FMath::RInterpConstantTo(AimRotation, DesiredAim, DeltaTime,
                                       AimSlewDegreesPerSecond);   // 240 °/s
AI->SetFocalPoint(BaseMuzzle + AimRotation.Vector() * 거리);
```

**등속 램프다.** 이 프로젝트의 다른 축이 전부 그런 이유와 같다(P71) — **어떤 방위에
올라타는 데 걸리는 시간을 숫자로 말할 수 있고**, 마지막 몇 도에서 기어가지 않는다.
하필 그 마지막 몇 도가 중요한 구간이다.

### 3.3 ★ 시야 콘도 **같은 회전을 읽는다** (P86)

`SetFocalPoint` 이 `AimRotation` 으로 놓이므로 **시야 판정의 콘도 그 회전을 본다.**

> **머리가 아직 안 돌아간 표적은 볼 수 없다.**

한계를 **소비하는 곳마다 한 번씩** 거는 대신 **양을 만드는 자리에서 한 번** 걸었다.
두 곳에 걸면 같은 제한이 두 번 적용되거나(둘 다 걸릴 때) **몸과 눈이 어긋난다**(한쪽만
걸릴 때).

### 3.4 귀결 — 새 의도 `Traversing`

```
FireIntent = Traversing        // 쏠 값어치는 있는데 총이 아직 안 왔다
발사 조건    AimErrorDeg ≤ WeaponSpreadDegrees × OnTargetConeRatio (1.0)
```

**선회 중에 나가는 탄이 사라졌다.** 그 탄은 총열이 지나가던 아무 데로나 갔다.
허용 오차를 **무기 자기 콘**으로 잡은 것도 같은 이유다 — 이 층의 모든 결정이 이미 그
양으로 재어진다. 1보다 작게 잡는 것은 **무기가 못 내는 정밀도를 요구하는 것**이다.

### 3.5 ★ `WantsToFire()` 를 긍정 열거로 써 둔 것이 **여기서 값을 했다** (P68)

열거형에 값을 **하나 더 넣는 일**이 안전했던 이유는 그 함수가 `!= Hold` 가 아니라
**두 발사 의도의 열거**로 쓰여 있었기 때문이다.

```cpp
return FireIntent == Aimed || FireIntent == Suppressive;      // Traversing 추가해도 무사
```

`Masked` 를 넣었을 때 **병사들이 아군을 관통해 쐈던** 바로 그 자리다.
**원칙이 값을 돌려준 첫 사례**이므로 적어 둔다.

## 4. 탄약과 재장전 — 오지 않는 소강상태를 기다리고 있었다 [A]

### 4.1 증상

원본 5절의 재장전 조건은 **소강상태**(`bLull = !WantsToFire()`)를 요구했다.
**그런데 접촉이 시야에 있는 한 쏠 값어치가 있는 탄은 거의 항상 있다.** 그래서 병사들은
**마지막 한 발까지 쏘고 탁 트인 곳에서 재장전했다.**

### 4.2 고친 조건

```
bEmpty                          → 무조건
그 외  MagFraction < ReloadBelowFraction 0.5
       AND bSafe = (Exposure ≤ MaxExposureToReload 0.5  OR  CanHideHere())
       AND (bLull  OR  CanHideHere())
```

**숨을 곳이 있다는 것 자체가 기회다.** 소강상태를 기다리는 대신 **몸을 낮출 데가 있는
순간**을 사면, 탄창은 **도약과 도약 사이에 채워지고** 도약 한복판에서 비지 않는다.

### 4.3 재장전은 **담 뒤에서** 한다

```cpp
if ((bWantsToReload || bReloading) && bCanDuck) { DesiredStance = 1.f; }
```

자세를 강제로 내리는 것은 **앞이 아니라 뒤에서 재장전한다**는 뜻이고, 동시에
**1.4절의 조리개 논리가 "없는 탄을 쏘려고 병사를 일으켜 세우는 것"을 막는다.**

### 4.4 제압 사격의 탄약 유보는 그대로

`SuppressiveReserveFraction 0.4` — **조준 사격은 자기 탄값을 하고 제압 사격은 하지 않는다.**

## 5. ★ 위치 비용의 교정 — 다섯 건 [A]

원본(`..._objective_and_position_cost.md` 2절)의 식은 세 항이었다.
**첫 항이 통째로 바뀌었고**, 둘째 항의 성질과 가중치가 바뀌었고, 후보 생성과 위협 추정이
바뀌었다.

```
Cost(자리) =  FightingCost(자리)                    ← 바뀐 자리 (전: 도착지 노출)
           +  RouteRiskWeight 0.6 × RouteRisk       ← 거리로 스케일 · 가중치 하향
           +  ObjectiveWeight  2.0 × ObjectiveCost
```

### 5.1 ★★ `FightingCost` — **완벽한 엄폐와 사격 위치는 반대말이다** (P82)

**증상**: 병사들이 **깊은 구석에 들어가 앉아 남은 전투 내내 아무것도 안 했다.**
플레이에서 관측된 그대로다 [A].

**원인**: 노출을 **최소화**하면 깊은 구석이 **만점**이다. 그리고 거기 있는 병사는
**맞을 수도 없고 쏠 수도 없다.** 최적화기는 자기가 시킨 일을 정확히 했다.

**고친 방법**: 높이 스윕이 **이미 만들어 두고 있던 두 사실**로 양쪽을 다 값 매긴다.

```cpp
bCanHide  = FirstHidden < Samples     // 어느 높이에선가 막힌다 = 숨을 것이 있다
bCanFight = FirstHidden > 0           // 맨 위 표본이 아직 보인다
                                      //   = 선 몸이 보인다 = 위협이 보인다 = 쏠 수 있다
```

```
!bCanHide   → NoCoverCost          1.0
!bCanFight  → NoFiringPositionCost 0.5
```

| 자리 | hide | fight | 비용 |
|---|---|---|---|
| **낮은 담** | ✅ | ✅ | **0.0** |
| 깊은 구석 | ✅ | ❌ | 0.5 |
| 탁 트인 땅 | ❌ | ✅ | 1.0 |
| (둘 다 아님) | ❌ | ❌ | 1.5 |

> **자리는 *선택지*가 있을 때만 값이 있다 — 웅크리면 보호, 서면 사격.**
> 그것이 정확히 "낮은 담이 무엇인가"에 대한 정의이고, **구석과 탁 트인 땅이 둘 다
> 나쁘게 매겨지는** 이유다.

`bCanFight` 가 **"선 몸이 보인다"와 같은 문장**이라는 것이 요점이다 — 한 스윕이 이제
**세 답**을 준다(노출 · 필요 자세 · 싸울 수 있는가). **새 트레이스는 한 발도 쓰지
않았다.**

`NoCoverCost` 를 **가장 큰 단일 항**으로 둔 것도 의도다. 나머지는 전부 선호이고
**이것은 총에 맞는 일**이다. 건너감보다 작으면 **탁 트인 곳에 잡힌 병사가 거기를 떠날
산술이 없다.**

### 5.2 ★ 경로 위험 — **거리로 스케일하고, 자리보다 싸게 매긴다** (P83)

**증상**: 병사들이 **스폰 지점에서 아예 안 움직였다** [A].

**원인**: `RouteRiskWeight` 가 1.0, 즉 **탁 트인 자리에 서 있는 값과 그 앞을 건너는 값이
같았다.** 그러면 **엄폐에 도달하는 이득이 도중에 보이는 대가를 절대 갚지 못한다** —
3m 앞의 담으로도 가지 않는다.

**고친 것 둘**:

```cpp
// ① 건너는 거리로 스케일한다
Span = clamp(Dist(From, To) / SearchRadiusCm, 0, 1);
return FractionSeen * Span;

// ② 가중치를 영구 노출보다 낮춘다
RouteRiskWeight 1.0 → 0.6
```

> **보이는 것은 사건이 아니라 비율이다.** 2초 보이는 것은 4초 보이는 것이 아니다.
> **건너감은 2초짜리 노출이고 자리는 무언가 바뀔 때까지의 노출**이므로,
> 두 개를 같은 가중치로 더하면 안 된다.

⚠ **표본은 여전히 직선 위에 있다. 네브메시 경로가 아니다** (P74의 표본 높이 규약은
그대로 유효하다 — **서 있는 가슴 높이**). → **[W20]**

### 5.3 후보를 **두 겹 링**으로 [W21 절반 해결]

```
Slot 짝수 → SearchRadiusCm (1200)
Slot 홀수 → SearchRadiusCm × InnerRingFraction (0.45) = 540
```

**증상**: 구석에 몰린 병사가 **한 반경의 후보를 전부 지오메트리 안에 두게 되고**,
전부 네브메시 투영에 실패하고, 스윕이 **아무것도 못 돌려주고**, 그 자리에서 남은 경기를
보냈다.

**가까운 링은 거의 항상 도달 가능하다.** 원본 [W21]이 지적한 "2m 앞의 완벽한 자리"는
아직 후보가 아니지만(링은 여전히 **고정 반경 둘**이다), **막다른 골목은 사라졌다.**

### 5.4 ★ 위협 추정을 **한 바퀴 동안 얼린다**

```cpp
if (!bBestValid) { SweepThreatEye = ThreatEye; bSweepHasThreat = bHasThreat; }
```

**한 틱의 트레이스 예산에 후보 하나가 들어간다.** 후보 12개짜리 한 바퀴는 **약 1/5초**가
걸리고, **그 사이에 위협이 움직인다.**

> **이른 후보를 "적이 있던 자리"로 재고, 지금 자리를 "적이 있는 자리"로 재는 것은
> 애초에 비교가 아니다.**

한 바퀴가 끝나면 다음 바퀴는 **새 추정으로 깨끗하게 시작한다** — 그래야 선택이
"여태 본 것 중 제일 좋은 자리"가 아니라 **지금의 세계**를 반영한다.

### 5.5 ★ 위협이 **없을 때의 의미론** — `bCanHide` 는 `true` 다

```cpp
if (!bHasThreat) { OutCanHide = true; return true; }
```

**아무도 안 쏘면 엄폐가 없는 자리란 없다.** `false` 로 두었더니 **마지막 접촉이 잊힌 순간
맵의 모든 자리가 `NoCoverCost` 를 만점으로 물었고**, 자리 사이의 차이가 전부 잡음에
묻혔다. 노출과 필요 자세가 0인 것(원본 5절)과 같은 계열의 판정이다 —
**숨을 대상이 없는 병사는 노출된 것이 아니라 그냥 밖에 있는 것**이다.

## 6. 목표 층의 교정 [A]

### 6.1 ★★ 루트 컴포넌트가 없었다 — **목표 층은 이번 라운드에야 처음 돌았다** (P90)

```cpp
// ASoldierObjective 는 맨 AActor 였다. 루트가 없는 액터는 위치를 가질 수 없다.
Anchor = CreateDefaultSubobject<USceneComponent>(TEXT("Anchor"));
RootComponent = Anchor;
```

**루트가 없으면 `SetActorLocation` 이 조용히 무시되고 `GetActorLocation` 은 영원히
월드 원점을 답한다.** 에러도, 경고도 없다.

즉 **여태까지 모든 목표 거리는 액터를 놓은 자리가 아니라 (0,0,0) 에서 재고 있었다.**
[W25]는 "레벨에 0개"로 적혀 있었으나, **한 개를 놓았더라도 그 라운드에는 여전히 안 돌았을
것**이다.

**고친 뒤 확인한 것** [A]: 레벨에 배치된 수비 엄폐가 전부 목표 비용 **0.00**
(`Low_Def_A/B` 1077cm · `Med_Def` 600cm) 또는 **0.05**(`Bld_Def_N/S` 1530cm)로 나온다.

### 6.2 공격 비용의 **천장을 없앴다** (P84)

```cpp
// ⛔ clamp(DistanceCm / ApproachScaleCm, 0, 1)
// ✅ DistanceCm / ApproachScaleCm
```

**천장은 그 너머를 평평하게 만들고, 평평한 비용에는 기울기가 없다.** 그 사거리 밖에서
시작한 공격수에게는 **한 걸음을 뗄 산술적 이유가 없었다.**

**비교되는 것은 후보 사이의 *차이*뿐이므로 절댓값은 얼마든 커져도 된다.**
0..1 통화를 지키려던 것이 오히려 이 항을 죽이고 있었다.

### 6.3 `ApproachScaleCm` 6000 → **3000**

**이 값은 미터를 "총 맞는 일"로 바꾸는 환율**이고, **그 접근이 실제로 다투어지는 깊이**로
잡아야 한다. **맵 크기로 잡으면** 한 번의 도약이 너무 값싸져서 **어떤 건너감도 자기 값을
못 갚고**, 공격은 **처음 만난 엄폐에서 멈춘다.**

### 6.4 ★ `RadiusCm` 900 → **1500**, `DefendBandCm` 900 → **1200** (P85)

**증상**: 수비수가 진동했다.

**원인**: 레벨에 놓은 수비 사격 위치가 **목표에서 1077cm** 에 있었다 — **옛 반경 900 바로
바깥.** 그래서 **땅은 안으로 당기고 엄폐는 밖으로 당겼고**, 병사는 그 사이를 오갔다.

> **지켜야 할 구역의 반경은 *싸울 만한 엄폐를 품을 만큼* 넓어야 한다.**
> 평평한 0 구간(P73)의 요점은 "수비수가 엄폐와 사계만 보고 고른다"인데,
> **고를 엄폐가 구간 밖에 있으면 그 요점이 성립하지 않는다.**

### 6.5 `ObjectiveWeight` 1.2 → **2.0**, `MoveImprovementMargin` 0.25 → **0.3**

`FightingCost` 가 최대 1.5까지 나오게 되면서 **세 항의 상대 크기가 달라졌다.**
`ObjectiveWeight` 는 여전히 **이 층의 유일한 성격 다이얼**이다 — 엄폐를 안 떠나는 병사와
목표를 위해 탄막으로 걸어 들어가는 병사 사이의 값이고, **용감하면서 동시에 신중한 설정값은
없다.** → **[C-94]**

## 7. 추측항법이 만료된다 [A]

```
FSoldierEnemyRecord.VelocityTrustSeconds = 1.5      (총성 기록은 0)
PredictLocation = Location + Velocity × min(나이, VelocityTrustSeconds)
```

### 7.1 ★ 속도에 대한 믿음은 위치에 대한 믿음보다 **먼저 죽는다** (P88)

**한 번 조깅하는 것을 봤다고 해서 10초 동안 같은 속도와 방향을 유지했다고 쳐 주는 사람은
없다.** 그런데 코드는 **기록이 살아 있는 내내** 그렇게 하고 있었다.

| | 20초 된 기록의 예측 |
|---|---|
| 전 | 마지막 목격 지점에서 **120m 앞** |
| 후 | **9m** 에서 멈추고, 그동안 **반경만 계속 열린다** |

> 후자가 말하는 것이 옳은 문장이다 — **"그는 여기 있었고, 지금쯤은 이 원 안 어디든 있을
> 수 있다."** 앞의 것은 **있지도 않은 환영**이고, 병사들은 그 환영을 향해 자리를 옮기고
> 조준하고 있었다.

### 7.2 총성 기록은 `0` 이다

**소리는 누가 어느 쪽으로 달리는지에 대해 아무 말도 하지 않는다.** 신선도·해상도를
분리해 든 것(P62)과 같은 계열 — **각 소스가 자기가 실제로 아는 것만 말한다.**

`VelocityTrustSeconds` 는 융합(P65)에서 **이긴 쪽의 값을 따라간다.** → **[C-96]**

## 8. 이동 배관 [A]

### 8.1 ★ 정지 감지 — "진행 중"은 **진척으로 묻는다** (P87)

**보고된 프리즈의 정체**: 아군 둘이 마주 보고 걸어 들어가면 **경로추종기가 영원히
`Moving` 을 보고한다.** 그리고 "진행 중인 이동은 안 건드린다"는 규칙(원본 7.4절)이
**재결정을 거부한다.** 둘은 남은 경기 내내 얼굴을 맞대고 서 있었다.

```cpp
bMakingProgress = Velocity.SizeSquared() > FMath::Square(StallSpeedCms 20);
bAlreadyGoing   = AI->GetMoveStatus() == Moving && bMakingProgress;
```

**타임아웃이 아니다.** 묻는 것은 **어디로든 가고 있느냐**이고, 그것이 실제로 중요한
것이자 **막힌 경로추종기가 계속 거짓말하는 바로 그것**이다.

### 8.2 RVO 회피를 **이동이 결정되는 곳에서** 켠다

```cpp
Movement->SetAvoidanceEnabled(bUseAvoidance);                  // BeginPlay, SoldierCover
Movement->AvoidanceConsiderationRadius = AvoidanceRadiusCm;    // 300
```

같은 편끼리 **서로를 통과해 걸어 들어가던 것**이 없어진다 — 보기에도 틀렸고,
8.1절 교착의 원인이기도 했다. **회피는 이동의 문제이므로 이동을 정하는 컴포넌트에 둔다.**

### 8.3 ★ 스프린트 — **규칙이 아니라 선호다** (P89)

```cpp
bWantsToSprint = Cover != nullptr && Cover->IsMovingToCover() && !WantsToFire();
```

**"위험하면 달려라"라고 쓰지 않았다.** 그것은 규칙이고, **규칙은 아무도 예상하지 못한
상황이 오는 순간 틀린다.**

이것은 **느릴 이유의 부재**다 — 움직이는 중이고, 쏘고 있지 않다.
**느림은 오직 사격을 안정시키려고 사는 것**이고, **쏘면서 움직이는 값은 이미 콘에
물려 있다**(2.1절). 위험한 땅이면서 동시에 쏠 값어치가 있으면 **사격이 이기고 병사는
느려진다** — 그것이 이것을 명령이 아니라 선호로 만드는 지점이다.

발행은 GASP 입력 상태 구조체의 `wantsToSprint` 로, `wantsToAim` 과 **같은 경로**로 간다
(`..._ai_bridge_and_scene.md` 4.2절).

> ★ **사용자가 명시적으로 요구한 규칙이다**: 이 층의 모든 것은 **선호**이고
> **상황별 하드코딩 규칙은 금지**다. → **P89**

## 10. 관전 모드 — 빙의 [A]

`..._ai_bridge_and_scene.md` 7절의 연장이다.

### 10.1 이동 방향은 `GetControlRotation` 에서 온다 (7.3절의 확정분)

`DefaultPawn` 은 `bUseControllerRotationPitch/Yaw = false` 라 **액터가 영영 회전하지
않는다.** 액터 벡터로 몰면 **+X 를 보고 있을 때만 WASD가 맞는다.**
**수직만 월드 업**으로 둔다 — 아래를 보고 상승 키를 눌러도 올라가야 하기 때문이다.

### 10.2 ★ 빙의 — 판정을 **Tick 에서** 한다 (P94)

```
Tick   조준선 아래의 병사를 찾아 HoverSoldier 에 저장하고 그 위에 "[F] 빙의" 를 그린다
F      저장된 그 대상을 빙의한다
```

**키를 누르는 순간에 판정하지 않는 것이 요점이다.** 그러면 **화면이 예고한 것과 키가
실행하는 것이 각각 다른 계산**에서 나오고, 둘이 어긋나는 순간이 생긴다.
**같은 값을 그리고, 같은 값을 실행한다.**

### 10.3 나가는 것도 같은 키 — 그리고 **`SpawnDefaultController()` 가 두 번째 단계다**

병사에서 F를 누르면 관전 폰을 다시 빙의한다. **그것만으로는 안 된다** —
**컨트롤러가 없는 폰이 남아 그냥 서 있는다.** `SpawnDefaultController()` 를 호출해야
AI가 재개된다.

### 10.4 ⚠ 입력은 Input Action 이 아니라 **직접 키 이벤트**다

**새 `InputAction` 에셋을 이 도구로 만들 수 없고**, `Config/DefaultInput.ini` 는
**읽기 전용**이다([W15] P4V와 엮인다). 그래서 직접 키 이벤트로 배선했다.
**도구 제약이 설계를 한 칸 옮긴 자리**이므로 적어 둔다(7.1절과 같은 계열). → **[W31]**

## 11. 디버그 [A]

### 11.1 ★ 엄폐 오버레이가 **비교의 양변을 다 찍는다**

```
exp 0.50 hide+fight obj 0.00 | HERE 0.00  best 0.35 +m 0.30 -> stay  (moving)
```

**현재 비용만 찍으면 실제 결정이 안 보인다.** 자리가 안정돼 보여도 **매 바퀴 비교에서
지고 있을 수 있고**, 그 경우와 "비교에서 이기는데도 움직인다"는 경우가 **화면에서 구분이
안 됐다.** 12절이 이 표시를 요구한 이유다.

### 11.2 교전 오버레이

```
AIMED  over/blind  know 120 vs weapon 340  recoil 0.54  ammo 17/30  reload?
```

**조리개/자세**와 **반동**이 붙었다. 새 의도 `Traversing` 은 자기 색(탁한 노랑)을 받는다 —
**행동은 앎의 출처 색을 빌리지 않는다**(P70).

⚠ 교전 디버그를 켜면 **`FindAperture` 가 틱당 한 번 더 돈다** — 즉 **사선 트레이스가
최대 4발 더** 나간다. 조리개 트레이스는 애초에 **예산 밖**이다(엄폐의 라운드로빈에
들어 있지 않다). → **[W32]** · **[C-83]**

## 12. ★★ 미해결 — **수비수가 자리를 잡고 쏘지 못한다** [A · 관측됨]

**증상**: 수비수가 **너무 자주 자리를 옮겨서** 정착해 사격하지 못한다.

**이번 라운드에 두 번 시도했고 둘 다 해결하지 못했다.**

| 시도 | 무엇 | 결과 |
|---|---|---|
| ① | **한 바퀴 위협 스냅샷**(5.4절) + **위협 없을 때 `bCanHide=true`**(5.5절) | ❌ |
| ② | **속도 신뢰 만료**(7절) + **목표 반경 확대**(6.4절) | ❌ |

> **다음 세션이 할 일은 세 번째 추측이 아니다.** 11.1절에서 오버레이가
> **HERE 비용 · 최선 후보 비용 · 여유**를 전부 찍게 만들어 두었으니,
> **어느 경우인지 읽는 것**이 먼저다.

```
① HERE 가 0 인 채로 유지되는데 그래도 움직인다
      →  비교는 맞는데 이동 발행이 잘못됐다.
         볼 곳: 한 바퀴 종료 블록 · bAlreadyGoing · MoveToLocation 재발행 ·
                8.1절의 정지 판정이 정상 이동까지 stall 로 읽는가

② HERE 가 진동한다 (hide / fight 가 뒤집힌다)
      →  위협 추정이 아직 불안정하다. 한 바퀴 스냅샷으로 부족했다는 뜻이다.
         볼 곳: GetPrimaryContact 의 대상 교체 · EvaluateRecord 의 반경 성장 ·
                bCanFight 가 표본 하나 차이로 뒤집히는 것 (HeightSamples = 3)

③ best 가 정말로 더 낮다
      →  가중치 문제다. 후보가 실제로 더 좋은 자리로 평가되고 있다.
         볼 곳: ObjectiveWeight 2.0 · RouteRiskWeight 0.6 ·
                MoveImprovementMargin 0.3 · FightingCost 두 상수
```

**셋은 서로 다른 고칠 자리를 가리키고, 화면 한 줄로 갈린다.** → **[C-95]**

> ⚠ **이 문제를 다시 추측으로 건드리지 말 것.** P10("임계값을 다루기 전에 계측부터")과
> P44("과도현상은 과도구간을 계측해야 보인다")가 같은 말을 하고 있고,
> 이번 라운드의 두 실패가 **정확히 그 둘을 어긴 결과**다.

## 16. 정정 (2026-09-14 오후) — 12절의 답

12절이 요구한 진단을 했다. 사용자 관측 **`HERE ≈ 1.0`(가끔 0.5)** — 세 갈래 어느 것도 아니었다.
**후보는 발(네비메시) 기준, HERE 는 캡슐 중심(+90 cm) 기준**으로 같은 담을 두 높이에서 재고 있었다.
같은 버그가 `RequiredStance` 를 항상 0 으로 만들어 "제압 없이는 안 웅크린다"의 원인이기도 했고,
`ThreatEye` 가 기록(이미 가슴) + 135 = **2.6 m** 였다. 10절의 관전 빙의는 `Possess` 라 AI 를 멈추므로 폐기.
→ **`2026-09-14_cover_frame_fix_and_observer.md`** · **P103**(처음 P100 으로 적었다가 이관 세션의 P100 과 충돌해 개명).
