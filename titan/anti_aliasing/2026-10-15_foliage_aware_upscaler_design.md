# 잎 인식 업스케일러(Foliage-Aware Temporal Upscaler) 기획

2026-10-15 / 설계단계 / TSR을 플러그인으로 복제해 교체하고, 잎 픽셀만 "기하로 판정하고 오래 누적"해 정적 잎 얼룩을 없애는 계획(엔진 수정 없음).

## 1. 목표와 비목표

- **목표**: 카메라가 멈췄거나 천천히 움직일 때, 나뭇잎(Megaplants Nanite Foliage)의 얼룩·반짝임을 DLSS 정지 화면 수준으로 없앤다. 리눅스(Vulkan) 전시 PC와 RTSP 송출 화면에서도 동작해야 한다.
- **비목표(1차)**: 파티클·화염·급격한 장면 변화의 품질 개선. 이 영역은 TSR 원래 동작을 그대로 유지한다. 지금보다 나빠지지만 않으면 된다.
- **비목표**: 잎 노멀이나 머티리얼을 바꿔 원본 모양을 바꾸는 방식. 수관 노멀 블렌드는 2026-10-14 사용자가 기각했다.
- **제약**: 엔진 수정 금지. 프로젝트 플러그인으로만 구현한다.

## 2. 지금까지 확정된 사실 (2026-10-14~15 trees 레벨 조사)

| 사실 | 근거 |
|---|---|
| 얼룩은 셰이딩 문제다. 잎 모양(커버리지) 문제가 아니다 | Unlit에서는 사라지고, Lighting Only·Detail Lighting에서는 남음 |
| 원인은 잎마다 다른 노멀이 픽셀보다 작은 크기로 섞이는 것이다 | 잎 노멀을 월드 위로 고정하면 사라짐 |
| Nanite·복셀과는 무관하다 | Nanite on/off 모두 발생 |
| 얼룩이 생기는 직접 지점은 TSR의 셰이딩 리젝션(과거 버리기) 판정이다 | `r.TSR.Visualize 0`에서 얼룩 모양 그대로 샘플 수가 무너졌다가 회복함 |
| 리젝션 감도를 낮추면 얼룩이 사라진다 | `r.TSR.ShadingRejection.ExposureOffset -4`부터 소멸(-3은 효과 없음, 엔진이 ±20으로 클램프) |
| 감도를 낮추면 파티클·화염에 잔상이 생긴다 | 같은 설정에서 관찰. 화면 전체에 적용되는 값이라 피할 수 없음 |
| 외곽의 듬성한 잎 깜빡임은 별개 문제다(커버리지) | 노멀을 고정해도 남음 |

결론: TSR은 "색이 크게 변했다 = 장면이 바뀌었다"로 판단한다. 그런데 잎은 노이즈 자체가 큰 색 변화라서 둘을 구분하지 못한다. **색이 아니라 기하(깊이, 속도, 재질 종류)로 "같은 표면인가"를 판정하면, 잎에서는 마음껏 오래 평균 낼 수 있다.** 이 기획의 핵심이다.

## 3. 엔진 수정 없이 가능한 근거 (엔진 소스 확인)

- `Renderer/Public/TemporalUpscaler.h`: `UE::Renderer::Private::ITemporalUpscaler`는 외부 업스케일러용 공식 인터페이스다. 구현할 함수는 `AddPasses`, `Fork_GameThread`, `GetMin/MaxUpsampleResolutionFraction`, `GetDebugName`이고, 히스토리는 `IHistory`로 엔진이 뷰별로 보관해 준다.
- `Engine/Public/SceneView.h:2688` `FSceneViewFamily::SetTemporalUpscalerInterface()`: 뷰 익스텐션의 `BeginRenderViewFamily`에서 등록한다. DLSS·FSR 플러그인과 같은 방식이다. **프레임마다 등록 여부를 정할 수 있으므로, cvar 하나로 엔진 TSR과 실시간 A/B 전환이 가능하다.**
- 입력(`FInputs`)으로 지터된 SceneColor(DOF 이후, 모션블러 이전), SceneDepth, SceneVelocity, 지터 오프셋, 프리익스포저, 아이 어댑테이션, 이전 히스토리가 들어온다.
- GBuffer(잎 판정용 셰이딩 모델): `Renderer/Public/SceneRenderTargetParameters.h:134` `GetSceneTextureShaderParameters(const FSceneView&)`로 `AddPasses` 안에서 접근할 수 있다.
- 셰이더: 플러그인 셰이더 폴더 매핑(`AddShaderSourceDirectoryMapping`)은 TitanFlickerMeter에서 이미 쓰고 있다. 엔진 공용 `.ush`는 그대로 include한다.

**한계 1**: 엔진 TSR 함수(`AddTemporalSuperResolutionPasses`)는 Renderer Private이라 플러그인에서 호출할 수 없다. "TSR을 부르고 잎만 손보기"는 불가능하고, **TSR 전체를 플러그인으로 복제(포크)**해야 한다.
- 규모: C++ `TemporalSuperResolution.cpp` 3,780줄(`FViewInfo` 참조 7곳 → 공개 API로 대체 필요), 셰이더 23개 파일 약 10,800줄.

**한계 2**: 엔진 TSR은 반투명을 별도 텍스처로 받지만, 외부 업스케일러 입력은 반투명이 이미 합성된 SceneColor다. 파티클 분리는 §6의 대안으로 처리한다.

## 4. 쓸 수 있는 정보 (DLSS보다 우리가 더 아는 것)

| 정보 | 출처 | 용도 |
|---|---|---|
| 잎 픽셀인지 | GBuffer 셰이딩 모델(Two Sided Foliage), 필요하면 커스텀 스텐실 | 잎에서만 새 판정, 나머지는 TSR 원래 판정 |
| 깊이 | SceneDepth | 재투영, 가려짐 해제 |
| 모션 벡터 | SceneVelocity | 움직이는 물체, 향후 바람(WPO) |
| 카메라 행렬(이전/현재) | View | 정적 월드는 깊이만으로 정확히 재투영 |
| 나무가 정적이다 | 현재 WPO 꺼짐(2026-10-06) | 재투영 오차 없음 |
| 지터 오프셋 | FInputs | 서브픽셀 누적 = 진짜 슈퍼샘플링 수렴 |
| 정답 이미지 | 같은 장면을 수백 프레임 지터 누적 | 품질 측정 기준, 단계 C 학습 데이터 |

## 5. 핵심 아이디어

1. **기하 기반 판정**: 잎 픽셀은 과거 버리기를 색 차이가 아니라 "잎 마스크 유지 + 깊이 일치 + 화면 안"으로 판정한다. 잎의 색 노이즈는 판정에 쓰지 않는다.
2. **픽셀별 통계 학습**: 평균과 분산(1차·2차 모멘트)을 누적한다. 원래 많이 떠는 잎 픽셀은 그 떨림을 정상으로 받아들이고, 분산을 크게 벗어나는 변화만 진짜 변화로 본다.
3. **휘도와 색조 분리**: 잎 노이즈는 대부분 밝기 변화이고 색조는 녹색 계열로 유지된다. 화염·트레이서·피는 색조가 바뀐다. 색조가 크게 벗어나면 즉시 과거를 버린다(파티클 최소 안전장치).
4. **움직임 적응 누적 길이**: 정지 시 64~128프레임까지 누적하고, 카메라가 움직이면 서브픽셀 이동량에 따라 줄인다.
5. **잎이 아닌 픽셀은 TSR과 동일하게 동작**: 포크한 TSR 코드를 그대로 쓰므로 파티클·차량·병사 품질은 지금과 같다. `ExposureOffset`은 기본값 0으로 되돌린다.

## 6. 구조

```
[렌더] → ★ TitanUpscaler (플러그인, ITemporalUpscaler) ★ → [블룸/톤매핑] → [RTSP 복사·화면]
             ├─ TSR 포크 패스들 (잎 아닌 픽셀: 원래 판정)
             └─ 잎 경로 (잎 픽셀: 기하·모멘트 판정 + 긴 누적)
             입력: 지터 SceneColor, 깊이, 속도, GBuffer(잎 마스크), 자체 히스토리
```

- **위치**: 엔진 TSR과 같은 자리라 메인뷰, RTSP 복사본(VisualizeDepthOfField 이후 복사), 화면에 모두 자동 적용된다.
- **반투명(파티클) 분리 대안**:
  - (a) 색조 판정(§5-3)
  - (b) 뷰 익스텐션 훅으로 반투명 직전 씬 컬러를 복사해 두고 차이로 반투명 덮임을 추정 — 훅 지점 존재 여부 확인 필요
  - (c) 반투명 머티리얼에 커스텀 스텐실을 써서 마스크로 사용
  - 1차는 (a)로 시작한다.
- **외곽 잎 커버리지 깜빡임**: 잎 마스크 경계에서 커버리지를 따로 누적한다(2차 목표).
- **선례 코드**: `Plugins/TitanFlickerMeter`(셰이더 매핑, 뷰 익스텐션, 비동기 리드백), `Plugins/UGVPathOverlay`(컴퓨트 패스, 마스크 시간 누적, 지터 보정).

### 단계 C (선택, 연구)
- 잎 경로의 판정 가중치를 작은 신경망으로 대체한다. 정답 이미지를 우리 엔진에서 무한히 만들 수 있다는 게 장점이다. 리눅스 추론(NNE, Vulkan)과 비용이 불확실해서 결과를 본 뒤 결정한다.

## 7. 잎 경로 알고리즘 상세

픽셀별 추가 히스토리(TSR 히스토리 옆에 1장 추가, 출력 해상도):
- 휘도 2차 모멘트 `M2`, 누적 수 `N`, 잎 플래그, 깊이

매 프레임, 잎 픽셀에 대해:
1. **재투영**: 깊이와 이전 View 행렬로 이전 좌표를 구한다(움직이는 물체는 속도 버퍼로).
2. **기하 판정** (하나라도 실패하면 N=0, TSR 원래 판정으로 넘김):
   - 현재 픽셀이 잎인가 — 경계는 1~2픽셀 팽창한 마스크 사용
   - 재투영 깊이가 히스토리 깊이와 상대 오차 안에서 일치하는가
   - 화면 안인가
3. **통계 판정**:
   - 휘도: |L − 평균| > k·σ + ε 이면 N 감쇠 (k는 3~4)
   - 색조 차이가 임계값을 넘으면 N=0
4. **누적**: TSR 셰이딩 리젝션 결과 대신 위 판정을 쓰고, 히스토리 블렌드 가중치는 α = 1 / min(N+1, Nmax(움직임))으로 한다. 서브픽셀 지터 누적은 TSR 업데이트 패스를 그대로 쓴다.

구체적 삽입 지점: `TSRRejectShading.usf`(리젝션 결과 출력)와 `TSRUpdateHistory.usf`(블렌드). 포크 후 잎 마스크를 입력으로 추가한다.

## 8. 측정과 검증

TitanFlickerMeter 점수가 눈과 맞지 않았던 이유는 픽셀 단위 차이를 재기 때문이다. 얼룩은 수 픽셀 크기 덩어리다.

1. **정답 이미지**: 카메라를 고정하고 지터를 켠 채 AA를 끄고 256~1024프레임을 평균 낸다.
2. **얼룩 지표**: 4×4·8×8 블록 평균 뒤 프레임 간 변화량(안정성)과 정답 대비 오차(편향). 잎 마스크 영역만 따로 본다.
3. **눈 판정**이 최종 기준이다. 지표는 A/B 비교와 회귀 확인용이다.
4. **시험 장면**: trees 레벨(정지, 느린 패닝, 빠른 회전), New_kadex_0811 교전(파티클 회귀), RTSP 송출, 리눅스 패키지 실기.

## 9. 진행 순서 (제안)

| 단계 | 내용 | 규모(추정) |
|---|---|---|
| B0 | 플러그인 골격: 업스케일러 등록 + 단순 패스(이중선형 업스케일) + cvar A/B 전환. 메인뷰·RTSP·SceneCapture·리눅스에서 우리 업스케일러가 실제로 타는지 확인 | 2~3일 |
| B1 | TSR 포크: 셰이더 23개 복제 + C++ 패스 구성을 공개 API로 이식. 목표는 엔진 TSR과 화면이 동일 (A/B로 확인) | 1~2주 |
| B2 | 측정 도구(정답 이미지 + 블록 지표) | 1~2일 |
| B3 | 잎 경로: GBuffer 마스크 + 기하·모멘트 판정 + 긴 누적 | 1주 |
| B4 | 튜닝: 움직임 적응, 색조 안전장치, 외곽 커버리지, 비용 측정, 리눅스 실기 | 1~2주 |
| C | 학습형(선택) | 연구 |

B1이 가장 크고 위험한 단계다. 막히면 대안으로, TSR 포크 대신 **자체 단순 TAAU(지터 누적 + 분산 클리핑) + 잎 경로**로 범위를 줄인다. 이 경우 잎이 아닌 영역의 품질이 TSR보다 낮아질 수 있다.

## 10. 위험과 미결 사항

- **인터페이스 안정성**: `ITemporalUpscaler`는 네임스페이스가 `Private`다. 엔진 버전을 올릴 때 바뀔 수 있고, 포크한 TSR도 따라가야 한다.
- **바람(WPO)을 다시 켜면**: 정적 가정이 깨지므로 속도 버퍼 기반으로 전환해야 한다. Nanite WPO 속도 출력 여부를 확인해야 한다.
- **자체방호 RTSP(SceneCapture 7개)**: 업스케일러 인터페이스가 캡처 뷰 패밀리에도 적용되는지 B0에서 확인한다. 환경카메라 일부는 지터를 끈 상태(`bAllowTemporalJitter=false`)다.
- **잎 판정**: Two Sided Foliage를 Megaplants 잎만 쓰는지, 풀(Grass)을 포함할지 정해야 한다.
- **에디터 뷰포트 vs PIE·패키지**: 화면 비율과 설정이 달라 결과가 다를 수 있다. 게임 쪽 `r.ScreenPercentage 50`의 출처 확인이 필요하다.
